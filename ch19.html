19一次真实交互的全程解剖

一句话：这一章不讲道理，只验尸——把一条真实导出的轨迹摊开，一条命令 rm -rf stale_cache.txt 从被拦下到被执行完，十条事件逐字段看完。实测

先交代这份材料的出身。它是官方 Cookbook 随附的轨迹导出（导出器自报 Muse Code 0.1.0，redaction: "raw"，即未脱敏原文）。整条会话的元数据是：session_id 为 c7dfaecc…，trajectory_id 为 trajectory_c7dfaecc…，root_session_id 与 session_id 相同（说明它就是根会话，不是子代理派生的）；共 2 个 turn、230 个 step；accepted_spawns 为空数组（没派过子代理）；session_end 是 {exit_reason: "clean", uptime_ms: 153580}——正常结束，存活约 153 秒。另有一处如实记录：saw_history_gap: true，导出自己承认这条轨迹的历史存在缺口，所以下面只解剖证据完整的那一段。

我们看的切片是 step 190–199，对应事件流序号 seq 193–202，共十条记录。一条高危命令的完整一生：被请求、被等待、被裁决、被接纳、被调度、被声明、被执行，全在里面。

第 0 步 · 信封：十条记录共用的外壳

envelope: {
  schema_version: 1,
  id: "9bf5c543-…",               // 本条记录自己的 UUID，每条都不同
  stream: { kind: "session", id: "c7dfaecc-…" },
  sequence: 193,                  // 流内序号，只增不改
  recorded_at: 1785704083894205,  // 微秒级时间戳
  record_type: "event",
  durability: "durable",          // 持久落盘，不是内存态
  causation_id: null,             // 本切片十条全为 null
  payload_type: "runtime.session",
  payload_schema_version: 2,
  payload: { … }                  // 正文，各步不同
}
derived: { session_id, trajectory_id, step_id: 190,
           turn_count: 2, decoded: true }

三个细节值得先记住。第一，derived 是导出时算出的索引层：不用解开 payload，就能按 session、step、turn 定位每条记录；其中 decoded: true 表示导出时这条 payload 能被完整解开，没有解不开的黑盒。第二，causation_id 这个「因果链」字段在十条记录里全是 null——这条链的配对并不靠它，靠的是 payload 里的业务 ID（后面会看到）。第三，时间：十条记录的 recorded_at 从 …894205 到 …898190，总跨度 3985 微秒，约 4 毫秒；相邻两条的间隔都在 296–796 微秒之间，是同一次机器处理里连着落盘的节奏。这个数字先放这儿，第 5 步揭晓它意味着什么。

还有一个坐标上的小发现：sequence 从 193 起，step_id 从 190 起，两者始终差 3。两种计数数的不是同一样东西——sequence 是这条 session 流里的事件序号，step_id 是轨迹的步数坐标，原点不同、步长相同，所以差值恒定。读这类导出时先把坐标系对齐，后面才不会把「第几条事件」和「第几步」混为一谈。另外注意 payload 里反复出现的三层流引用：session_stream、run_stream、task_stream——同一件事在会话、运行、任务三条流上都有坐标，事件写在哪条流、引用哪几条流，是这套结构组织数据的骨架。

第 1 步 · seq 193：审批被发起（approval / requested）

payload: { kind: "approval", run_id: "002a75f8-…",
 event: { kind: "requested",
  pending_action_id: "a54bb4eb-…",
  task_id: "a54bb4eb-…",              // 与 pending 同值
  tool_call_id: "call_019fc441e26273d18c2dc570b154c39c",
  tool_name: "bash",
  raw_args: "{\"command\": \"rm -rf stale_cache.txt\",
    \"workdir\": \"/tmp/billing_demo\", \"shell\": \"bash\",
    \"login\": false, \"tty\": false, \"yield_time_ms\": 5000}",
  idempotency_key: "tool:call_019fc441e26273d18c2dc570b154c39c",
  approval_subject: { kind: "shell_command",
    raw_command: "rm -rf stale_cache.txt",
    stages: [ { requirement_id: { pending_action_id: "a54bb4eb-…",
                  source_index: 0 },
      source_position: 1, total_stages: 1,
      argv: ["rm", "-rf", "stale_cache.txt"],
      argv_complete: true,
      prefix_candidates: [ ["rm"], ["rm","-rf"],
                           ["rm","-rf","stale_cache.txt"] ],
      resolution: { kind: "unresolved" } } ],
    canonical_workspace_root: "/tmp/billing_demo" },
  available_choices: [
    { choice_id: "allow_once", label: "Allow once",
      decision: { kind: "approved" } },
    { choice_id: "allow_local_prefix",
      label: "Always allow in this workspace: rm ...",
      decision: { kind: "approved_policy_amendment", … } },
    { choice_id: "abort", label: "Reject",
      decision: { kind: "abort" } } ],
  candidate_decisions: [ … ] } }

这一条是十条里最胖的，因为它要把「批什么、能怎么批」一次说全：

  • raw_args 全文保存：模型给 bash 的参数一个字不改地存下来，包括 workdir、shell、连 tty 和 yield_time_ms 都在。审批审的是原文，不是摘要——日后对账，账本里就是这串字符。
  • 命令被结构化拆解：approval_subject 把命令拆成 stages（本例只有 1 段），每段有 requirement_id、argv 数组、argv_complete 标记。为什么拆？复合命令可以逐段裁决，而不是整条一刀切。这次只有一段，所以 source_index 0、total_stages 1。
  • prefix_candidates 与 suggested_prefix：系统把 argv 的各级前缀都算了出来（["rm"]、["rm","-rf"]、全命令），还附了一份建议前缀及其出处（提取器版本、语法包 @withfig/autocomplete 的版本与哈希）。这是给「长期放行」选项准备的弹药：放行哪一级前缀，要有据可查，不能拍脑袋。
  • available_choices 是三个，不是两个：只许一次（allow_once）、在本工作区永久放行某前缀（allow_local_prefix，本质是一次策略修订 approved_policy_amendment，规则形态是 shell_command_argv_prefix 并绑定 workspace_root）、拒绝（abort）。审批卡上用户点什么，背后就是这三个 choice_id。
  • resolution 此刻是 unresolved：stage 的裁决槽位在发起时就留好，值是「未决」。状态机的位置是预先刻在数据结构里的。
  • 「永久放行」选项的完整形态：allow_local_prefix 的 decision 不是简单的 approved，而是 approved_policy_amendment，里面装着一条完整的策略修订：effect 为 allow、durability 为 local_persistent（本地持久）、rule 的 kind 是 shell_command_argv_prefix、argv_prefix 是 ["rm"]、workspace_root 锁定 /tmp/billing_demo、reason 为 null。也就是说，用户点下「总是允许」的那一刻，系统要写的不是一个布尔值，而是一条带作用域（只在这个工作区）、带形态（只匹配这个 argv 前缀）的新规则——这条记录把规则的全文提前备好了。
  • candidate_decisions 是给裁决方的速览表：三个候选结论各带一个 matcher 字段：approved 的 matcher 为 null（直接裁决即可）、approved_policy_amendment 的 matcher 是 shell_command_argv_prefix（要走前缀匹配这条路）、abort 的为 null。它和 available_choices 的区别是：choices 是给人看的选项（带 label），candidates 是给裁决逻辑看的索引。
  • suggested_prefix 的 provenance（出处链）：建议前缀不只给结论，还给全套出处——extractor_version（claude-code-2.1.207）、行为语料的版本与 SHA-256、语法包 @withfig/autocomplete 的版本号、git head、dist 完整性哈希、归一化 JSON 的哈希。一个「建议」都附带可复算的出处，这是整份导出的一贯风格：任何自动生成的判断，都要能回答「你凭什么」。
  • execution_context 与 current_requirement_id：前者把 canonical_workspace_root 再钉一次——执行环境的工作区根目录以规范化路径为准，不许用相对路径蒙混；后者指明当前正等待裁决的是哪个 requirement（就是 source_index 0 那个），让审批界面不用遍历 stages 也知道先处理哪一段。

第 2 步 · seq 194：等待开始（approval_wait.effect.started）

payload_type: "approval_wait.effect.started"
payload: { kind: "approval_wait_effect", run_id: "002a75f8-…",
 record: { kind: "started",
   pending_action_id: "a54bb4eb-…", task_id: "a54bb4eb-…",
   run_stream: { kind: "run", id: "002a75f8-…" },
   task_stream: { kind: "task", id: "a54bb4eb-…" },
   tool_call_id: "call_019fc441…", tool_name: "bash" } }

注意 payload_type 变了：上一条是 runtime.session（会话事件），这条是独立的 effect 事件。它只带配对所需的最小信息：哪个 pending、哪个 task、哪个 tool_call。为什么要单独有这么一条？因为「等待」本身被建模成一个有生命周期的对象——有 started，就必须有 terminal 来关它。流程的挂起状态不写在任何进程里，就写在这条记录里；进程死了、机器换了，这条 started 还在，等待就还在。

第 3 步 · seq 195：单个 stage 的裁决落定（stage_requirement_resolved）

event: { kind: "stage_requirement_resolved",
  pending_action_id: "a54bb4eb-…",
  requirement_id: { pending_action_id: "a54bb4eb-…",
                    source_index: 0 },
  choice_id: "direct:{\"kind\":\"approved\"}",
  decision: "approved", policy_result: "allow",
  amendment: null,
  resolution: { kind: "allow_once" } }

裁决是按 stage 粒度落的：requirement_id 精确指回第 1 步那个 source_index 0 的段。三个字段各管一件事：decision 是裁决本身（approved）；policy_result 是它在策略层的结果（allow）；resolution 是生效方式（allow_once，只许这一次）。amendment 为 null，说明裁决方没有顺带写入策略修订——如果选的是「永久放行前缀」，这里就会躺着那条新规则。choice_id 是个有意思的编码：direct:{"kind":"approved"}，把「直接裁决、内容是 approved」压进了一个字符串里。

第 4 步 · seq 196：裁决被正式应用（decision_applied）

event: { kind: "decision_applied",
  pending_action_id: "a54bb4eb-…",
  decision: "approved", policy_result: "allow",
  amendment: null,
  stage_evidence: [ { requirement_id: { …, source_index: 0 },
    source_position: 1, total_stages: 1,
    argv: ["rm", "-rf", "stale_cache.txt"],
    resolution: { kind: "allow_once" } } ],
  decision_source: { kind: "llm_judge",
    prompt_version: 1, params_version: 2,
    context_digest: "sha256:092e6c96…" } }

为什么 resolved 之后还要一条 applied？因为「作出裁决」和「裁决生效」是两个时刻：前者是某段的结论，后者是把全部 stage 的证据汇总、钉成正式记录。stage_evidence 就是证据袋：每个 stage 的 argv 原样再存一份——被批准的到底是哪几个参数，白纸黑字，不许事后口径漂移。decision_source 记录裁决者是谁、用的第几版提示词与参数、以及裁决那一刻上下文的 SHA-256 指纹（context_digest）。有了指纹，任何一次裁决都能回答「它当时是看着什么做的决定」，且可复算验证。

第 5 步 · 关于裁决者：这条轨迹的批人不是人

decision_source.kind 写得明明白白：llm_judge。也就是说，这份官方演示轨迹里的审批，是由一个自动裁判（LLM judge）完成的，不是真人点击。第 0 步那个「全程约 4 毫秒」的时间跨度与此完全吻合——真人不可能在 4 毫秒里看完命令并点批准。如实说明这一点，不影响结构的真实性：事件类型、字段、配对方式都是产品真实用的那套；只是坐在裁决位上的，在这条演示轨迹里是自动裁判，在真实产品使用中可以是用户本人。seq 200 里还会出现 policy_decision: "allow:llm_judge"，把这次裁决的依据一路带到执行门口。

第 6 步 · seq 197：等待终结（approval_wait.effect.terminal）

payload_type: "approval_wait.effect.terminal"
payload: { kind: "approval_wait_effect", run_id: "002a75f8-…",
 record: { kind: "terminal",
   pending_action_id: "a54bb4eb-…",
   outcome: { kind: "approved" } } }

这是与第 2 步配对的那一半：同一个 kind（approval_wait_effect）、同一个 pending_action_id，一个 started、一个 terminal，中间夹着裁决的两条记录。恢复逻辑要找「还没关上的等待」，就是在流里找有 started 无 terminal 的 pending_action_id；要找「刚被放行的动作」，就看 terminal 的 outcome。这条记录本身极简，因为它需要的只是「关门」这个事实和结论。

第 7 步 · seq 198：任务被接纳（task / accepted）

payload: { kind: "task", run_id: "002a75f8-…",
  task_id: "a54bb4eb-…",
  event: { kind: "accepted", task_id: "a54bb4eb-…" } }

从这里起，payload 的 kind 从 approval 切换为 task，payload_schema_version 也从 2 降为 1（两类事件各自演进）。审批通过不等于立刻执行：动作先回到任务系统，被正式「接纳」。为什么多这一跳？因为审批和执行是两个子系统，审批只负责放行与否，任务系统才负责排队、调度、留痕。accepted 就是两个系统之间的交接单。补一句版本细节：整条切片里，approval 类的三条 runtime.session 事件用的是 payload_schema_version 2，task 类的四条用 1，两类 effect 事件也用 1——版本号是按 payload 类型各自独立的，说明这几类事件的格式在不同时间点冻结，读取端必须按类型分别解码，不能指望一个版本号管全部。

第 8 步 · seq 199：任务被调度（task / scheduled）

event: { kind: "scheduled", task_id: "a54bb4eb-…",
  idempotency_key: "tool:call_019fc441e26273d18c2dc570b154c39c" }

idempotency_key 第二次出现。它在第 1 步由 tool_call_id 派生（tool: 前缀 + call id），在调度这一步被再次写明。理由很实际：调度可能重试、恢复可能重放，执行端认的是这把钥匙——同一把钥匙只执行一次。把钥匙在每个关键环节都显式带上，而不是指望谁「记得」，是这套数据结构的通用手法。

第 9 步 · seq 200：副作用意图声明（task / side_effect_intent）

event: { kind: "side_effect_intent", task_id: "a54bb4eb-…",
  operation: "tool:bash",
  idempotency_key: "tool:call_019fc441…",
  policy_decision: "allow:llm_judge",
  cancellation_handle: null,
  parent_task_id: null }

动手前先落一笔「意图」：我要执行什么操作（operation）、凭哪次裁决（policy_decision，把 llm_judge 的 allow 一路带到这里）、幂等钥匙是什么（第三次出现）。这笔记录的价值在出事时才显形：若执行中途崩溃，恢复时先查意图账——有意图无结果，说明事可能办了一半，要先核对再决定补办还是作罢。cancellation_handle 是预留的取消把手（本例为 null）；parent_task_id 为 null，标明它不是任何子任务，是一条顶层执行。

第 10 步 · seq 201：执行开始（task / started）

event: { kind: "started", task_id: "a54bb4eb-…",
  span_id: "ed7e2c608864e15c" }

全条最短的记录之一，只多了一个新字段 span_id：16 位十六进制，是给可观测系统用的调用链标识。执行从这里起进入 tracing 的世界——后面这条命令跑了多久、输出什么、退出码多少，都挂在这个 span 上。账本（事件流）管「该不该做、谁批准的」，span 管「做得怎么样」，两套记录各管一段，在 task_id 上汇合。

第 11 步 · seq 202：工具批次开始（tool_batch.effect.started）

payload_type: "tool_batch.effect.started"
payload: { kind: "tool_batch_effect", run_id: "002a75f8-…",
 record: { kind: "started",
   effect_id: "a54bb4eb-…",
   model_call_index: 0,
   task_id: "a54bb4eb-…",
   call_id: "call_019fc441e26273d18c2dc570b154c39c",
   tool_name: "bash",
   parallel_profile: { kind: "ineligible" } } }

最后一环，执行被登记为一个 tool_batch effect：effect_id 再次等于 a54bb4eb…，与 pending_action_id、task_id 三值同体。model_call_index: 0 标明它属于本轮模型产出的第 0 个工具调用批次。call_id 就是第 1 步的 tool_call_id，绕了一圈，执行端认的仍是模型最初发出的那个编号。parallel_profile: ineligible 直译是「不具备并行资格」——这条命令被明确标记为不可与其他工具并行执行，删除类操作串行到底，是写在数据里的约束。

把十条记录按配对关系收一遍，会看到三种不同的「成对」：第一种是生命周期配对——approval_wait 的 started（194）与 terminal（197）是一对，tool_batch 的 started（202）在切片内只有开始、终结在切片之外；凡是 effect，都有头有尾，找「悬挂未关」的对象就是找只有头的那一半。第二种是阶段配对——裁决的 resolved（195）与 applied（196）是一对，前者是单段结论、后者是汇总生效，中间不许跳过：没有 applied，resolved 只是一份草稿。第三种是子系统交接——approval 家族（193、195、196）把棒交给 task 家族（198–201），交接点是 accepted；两个家族共用同一套 ID，所以交接不丢线头。整条链的可靠性不来自某一条记录写得多全，而来自这三种配对都没有断。

切片之外：诚实边界

最后说清这章没看到什么。切片之前：用户的原始输入、运行时组装上下文的那一刻、模型推理产出这个 tool_call 的记录，都在 seq 193 之前，不在这份导出里。第 1 步的 raw_args 是从 requested 事件里读到的原文，这是实测；但「模型当时读到的上下文长什么样」只能按字段反推：turn_count 是 2、step 已经走到 190，说明这是第二轮对话里很靠后的一步，前面有 189 个 step 的历史——历史的具体内容不在切片内。合理推断

切片之后：seq 202 只是 tool_batch 的 started。命令的实际输出、退出码、工具结果如何回注上下文、模型读到结果后说了什么、最终答复的文本，都不在这十条里。会话层面只知 session_end 是 clean 收尾、总存活约 153 秒。把这些空白明说出来，和把字段讲透同样重要：这份切片能证明的，是「一次高危调用从发起到执行门口，每一步都被记录、被配对、被钉死证据」；它不能证明执行结果本身。

还有两处元数据层面的保留。其一，saw_history_gap: true 是会话自己声明的——这条轨迹在导出视角下历史并不完整，所以本文所有结论只对 seq 193–202 这段证据完整的区间负责，不外推到整条会话。其二，is_copied_context: false 说明这条会话不是从别的会话拷贝上下文起步的，是一条原生的根轨迹（与 root_session_id 等于 session_id 互相印证）；这保证了我们看到的审批链不是从某次分叉里继承来的半截状态。至于导出文件头里的 redaction: "raw"，它保证了字段是原文而非脱敏改写——本章引用的每个值，都与文件里的字节一致。
