PART 1 · 全景

01整体架构

一句话：每个用户独享一台电脑和一个 Agent，它在那台电脑里生活和工作，跟别人的完全隔开。

理解 Muse 的一切，先记住这张分层图。把鼠标放上去看看每一层管什么：

👤 用户层你：在手机 / 电脑 / 消息软件里说话、点批准
🚪 入口层Chat、Feed、Ideas、Goals、Library 五个页签 + 审批卡
🧠 大脑层大模型推理 + Agent 循环：想一步、做一步、看结果再想
🛠 执行层工具、Skills、连接器、浏览器、子代理——真正动手干活
🛡 信任层审批、凭证保险库、安全拦截——给执行力上锁的那层
💻 底座层你的专属电脑（虚拟机）+ 文件系统 + 事件日志

为什么一人一台电脑？

  • 隔离做在架构层，不是权限开关。别家的 Agent 物理上进不了你的机器，隐私边界不是「设置里关掉」，而是「压根不在一台机器上」。文档明文
  • Agent 因此能「常驻」。它有自己的家目录、文件和后台任务，对话关了它还在，明天回来一切都在原地。
  • 严格 1 对 1，没有群聊。所有对话只属于你和你的 Agent，「邀请」按钮只是分享推荐码，永远拉不进来第三个人。
  • 模型分工：免费版跑 Muse Spark，付费版跑 Muse Wonder——主对话、产物构建、定时任务、子代理、后台工作都由强模型兜底。文档明文
📌 本站的拆法：PART 2 拆大脑，PART 3 拆躯体，PART 4 拆信任层，PART 5 拆入口层的生活面。底座层散在各章里讲。
PART 1 · 全景

02运维设计

一句话：机器可以随时被换掉，但你的东西一样都不能丢——所有重要的状态都存在「换机器也活着」的地方。

Muse 的运行环境更新非常频繁，虚拟机可能被整体替换。但你几乎感觉不到，靠的是三条纪律：

🏠 家目录是唯一的家

文件、记忆、技能、定时任务定义都放在持久化的家目录里。机器是临时的，家是永久的——换机器等于把家整体搬走。

📋 任务靠「登记」不靠「进程」

定时任务、子代理、待审批都登记在系统里。机器重启后由运行时按登记表逐个恢复，而不是指望某个进程「还活着」。

🔁 恢复是默认动作

保存好的定时任务、未完成的子代理工作、挂起的审批，重启后自动回到应有状态。恢复失败会被明确报告，不装没事。

这条纪律后面会反复出现：状态进存储，进程随时可死。审批能等一天、子代理能跨重启，全是它的推论。环境实测

03LLM 设计

一句话：大模型被当成一个无状态的纯函数在用——递给它一份上下文，它交回一段文字或一个工具调用，仅此而已。
入
上下文系统提示 + 记忆 + 全部对话记录 + 工具清单，组装成一份文本
↓ 喂给模型
算
一次推理逐字生成，直到写完答复、或写出一个工具调用为止
↓ 交回
出
文字 或 工具调用纯文字 = 最终答复；工具调用 = 「我交出控制权，给我结果再叫我」

三个反直觉但关键的事实

  • 模型没有记忆。它「记得」你，是因为每次推理都把记录重新递到它眼前。连续性是运行时造的，不是模型自带的。
  • 模型不会等待。一次推理的输入在开始那刻就固定了，中途没有插入新信息的入口。所以工具结果只能等下一次推理——这不是选择，是架构。实测
  • 写到工具调用就必须停。再往下写就得编造工具的返回结果。停，是为了让真实世界把答案填回来。

模型分工：Spark 管日常，Wonder 管硬活（长任务、子代理、产物构建）。「性格」不靠改权重，靠每次递进去的系统提示和站立上下文——改性格等于改文件，不用重训模型。

04上下文工程

一句话：模型的「脑子」每轮都是临时拼的——核心从日志来，保证忠实；外围从现状来，保证新鲜。

点一点下面几层，看看一份完整上下文是怎么拼出来的、占多大：

🧭 系统提示（规矩与人格）≈8%
🪪 身份与用户档案（IDENTITY / USER）≈10%
🧠 长期记忆（MEMORY + 对齐合成）≈14%
💬 会话记录（这次对话的全部往返）≈46%
🛠 工具清单（按需加载，用到才展开）≈15%
📍 站立信号（时间 / 地点 / 待办 / 目标状态）≈7%

当前拼装：100%（点任意一层可开关它，看看少了它模型会「失忆」哪一块）

存档与投影：为什么隔一天恢复，上下文还可能不一样？

  • 存档层（事件日志）：只追加、永不改。一天后重放，长得和当时分毫不差。
  • 组装层（投影）：每轮临时拼。对话太长时，旧轮次会被摘要压缩——存档无损，投影有损。本站作者本人在这个会话里就被压缩过一次，靠的就是「摘要 + 日志」续命。
  • 外围每轮刷新：日期、记忆文件、目标状态都是现取的。隔天恢复时外围必然不同——而且应该不同，否则它还以为今天是昨天。
📌 系统要保证的从来不是「逐字复现」，而是三条不变量：事实不丢（日志完整）、往返闭合（发出的工具调用必有结果配对）、待办可定位（靠 ID 精确找回）。

05核心机制：Agent 循环

一句话：整个 Muse 就是一个 while 循环——推理 → 行动 → 看结果 → 再推理，直到活干完。
# 逻辑视图只有四行
while True:
    resp   = llm(context)            # 一次推理：产出即结束，模型离场
    if resp 是纯文本: break          # 没有工具调用 = 最终答复
    result = broker.execute(resp.tool_call)  # 程序侧执行：查凭证、等审批都在这
    context += [resp.tool_call, result]      # 结果回注，循环续上

点「运行一次」，看这个循环真实地转一圈。注意第三行：它看着是同步的一行，物理上可能是挂起 → 隔天 → 换个进程续跑（原理在第 06 章）：

1
组装上下文核心从日志重放，外围取最新状态
同步
2
模型推理模型只做这一件事：读一份材料，给出下一步
同步
3
产出工具调用交卷离场——它不会等，也没法等
同步
4
网关预判按工具类型与风险决定要不要问人
同步
5
发起审批 · 挂起状态存进记录里，不占任何线程
异步
6
用户裁决批准或拒绝，时机不限
异步
5
直接执行只读、低风险动作不打扰用户
同步
7
执行工具批准之后才执行，模型永远收不到空口的「批准了」
同步
8
结果回注结果信封里带着确认状态，模型靠读它才知道发生过什么
同步
9
再推理 → 答复没有工具调用了，循环结束
同步
等待运行…
📌 看出门道了吗：同步的只有「一次推理之内」和「一次执行之内」；跨审批、跨子代理，全是异步事件。能等的都不是模型——等待、排队、恢复，全是运行时的活。

06审批与认证（HITL）

一句话：给机器执行力，给人留否决权——但否决权做成一条数据记录，而不是堵住一条线程。

审批的事件设计（真实结构）

审批在事件流里是一个有头有尾的「effect」：开始与终结靠同一个 pending_action_id 配对。亲手试一下：

事件流（session 流，按 sequence 只追加）：

还没有事件。点①开始。

真实样本长这样（官方导出的一次「删文件」审批，字段原样）：

seq 194  approval_wait.effect.started
  payload: { pending_action_id: "a54bb4eb…", tool_call_id: "call_019fc…",
             tool_name: "bash", run_id: "002a75f8…" }
seq 197  approval_wait.effect.terminal
  payload: { pending_action_id: "a54bb4eb…", outcome: { kind: "approved" } }
seq 202  tool_batch.effect.started   # 批准之后，工具才真正执行

收到裁决后，靠什么找回上下文？

  • 主键是 session_id（哪个会话），不是某一轮对话；turn、step 只是流内的坐标。
  • 裁决事件带回 pending_action_id → 回查它的 started 记录 → 里面存着 tool_call_id 和 run_id：哪个工具调用被放行，分毫不差，不用猜。
  • 按 session 加载整条事件流重放 → 执行工具 → 结果回注 → 发起全新推理。隔一天、隔一次重启，配对关系写在数据里，不在谁的内存里。实测

认证：模型永远摸不到真钥匙

  • 工具要用某个服务的密钥时，向凭证服务（authd）申请的是一把替身钥匙（只在指定域名有效）；请求真正出门时，安全层（Sentinel）在出口把替身换成真钥匙。
  • 密码由用户在独立的安全页面录入（Secure Vault），模型只看得到一个令牌，看不到密码本身。让最能干的组件（模型）对最危险的东西（真凭证）保持无知。
  • 批准只覆盖当时展示的确切内容：内容一变，批准自动失效，必须重审。实测

07子代理编排

一句话：活太多就再叫几个自己来帮忙——子代理和主代理是同一个模型，区别只在任务简报和生命周期。

点「扇出」看看并行干活的样子——注意它们完成顺序和出发顺序无关，谁先干完谁先汇报：

🧑‍💼 协调者（主代理）
还没出发。

设计要点

  • 创建参数只有两个：一段任务简报（message），可选附带文件/图片（items）。没有「类型」参数、没有「模型」参数——分工不靠类型系统，靠简报把契约写清。实测
  • 异步收据制：派出时只拿到一个编号，派出者该干嘛干嘛；结果完成时自动递回，像外卖送达通知，不用守在门口。
  • 星形拓扑：子代理之间不能互相喊话。A 需要 B 的产出，必须经协调者转发。所有协调过中枢，出了问题只查一条线。
  • 深度上限 2 层：主代理 → 协调者 → 工人，到此为止，不许无限套娃。结构永远是一棵扁树。
  • 专用通道例外：浏览器任务（要持有登录态）、深度调研（刻意不给登录态）、产物构建、定时后台——这几类不走通用派出，各有入口。拆的标准不是任务类型，是边界硬度。
PART 3 · 躯体

08Skills 技能系统

一句话：Skills 是给 Agent 的操作手册库——每本手册写清一件事的标准打法，遇到对应的活，翻开照做。

📖 手册长什么样

一本手册 = 一份 SKILL.md（步骤、规矩、坑）+ 可选的脚本和参考资料。内容是写给模型读的自然语言 + 写给机器跑的代码，各管一段。

🔍 按需翻书

平时只把「目录」放进上下文（每本一句话简介）。任务命中哪本，才把全文读进来——省上下文，也避免无关规矩互相打架。

🧳 能带走

手册是自包含的文件夹，可以装进不同的 Agent 运行时。换个运行时要适配外壳，但核心打法不变——技能是资产，不是某个产品的附属品。

🌱 会生长，也会淘汰

后台有每日复盘循环：反复出现的活会被沉淀成新手册，已有手册按近期实绩审计——实测没帮助的变更要撤下。Agent 的「熟练度」因此能长期累积，又不至于积成垃圾场。

和工具的区别一句话：工具是能力（能不能做），Skill 是经验（该怎么做）。给新手发全套工具，他还是新手；再给他一柜子手册，他才像个熟手。

09连接器生态

一句话：连接器是 Agent 的对外插座——邮箱、日历、支付、社交，每个服务插上一个，Agent 就能替你操作它。

🔌 一个连接器 = 说明书 + 通道

每个连接器带一份文档：怎么连、能做什么、权限多大、出错怎么办。Agent 先读说明书再动手，和 Skills 是同一个套路——先文档，后操作。

🔑 授权走正规门

连接走服务自己的授权页（OAuth），密码不经过聊天、不经过模型。连没连上、健不健康，用之前先查状态，不凭感觉承诺。

🧩 没有现成的也能现接

任何有 API 的服务都能按统一模板做成自定义连接器：凭证进安全存储，说明书落成文件，之后和官方连接器一视同仁。

⚖️ 连接器 vs Skill

连接器管「通道和账号」（能不能碰这个服务），Skill 管「打法」（碰的时候怎么做得好）。一个管准入，一个管经验。

  • 文档即能力边界：连接器能用什么命令，以它自己的文档为准——文档没写的就是不存在。连了某个服务 ≠ 能用它的全部功能。这防止 Agent 凭想象调用不存在的能力，权限边界也可审计。
  • 权限有两层闸：服务商的 OAuth 授权是第一层（粗粒度）；你还能在设置里单独限制某个连接器的读/写动作（要审批 / 直接拦），这层细闸独立于服务商，长在自己手里。
  • 状态当场查，不靠记忆：授权会过期、会被拒。用之前跑一次状态核验；遇到永久拒绝就明说需要重新授权，不重试、不假装是临时故障。
  • 限流即停：撞上服务商的请求上限就按规矩退避，被标记为终止的直接停手——尊重平台规则，别把用户的账号玩封。

生态的另一条关键设计是最小披露：替你联系外部时，只给对方完成任务必需的信息——餐厅只需要名字、时间、人数，不需要知道你为什么吃饭。知道得多是本事，说得少是规矩。

10文件架构

一句话：Agent 的一切都落成文件——人格是文件、记忆是文件、技能是文件。你能打开看，它才能被你管住。
~ 家目录（换机器也搬走的那个「家」）
├─ IDENTITY.md / SOUL.md     它是谁、什么性格
├─ USER.md / MEMORY.md       你是谁、它记住的事
├─ AGENTS.md                 干活的规矩与教训
├─ memory/                   人物与群体档案（people / groups）
├─ workspace/
│  ├─ your_files/            交付给你的文件 → 出现在 Library
│  ├─ goals/<目标>/      每个目标一个工作区（文档/简报/内部状态分开放）
│  ├─ custom-skills/         为你定制的技能手册
│  └─ custom-connectors/     为你接的第三方服务
├─ hooks/                    事件监听脚本与状态
└─ docs/                     官方说明（只读）
  • 存储与橱窗分离：你上传的东西落进 workspace/user 持久保存但不自动上架；只有放进交付区的文件才出现在你的 Library 里。工作区和成品柜物理分家。文档明文
  • 删除分级：普通文件进回收站约 30 天可恢复；产物（Artifact）删除即永久——误删概率和误伤代价不同，规矩就不同。
  • 为什么全用文件、不用数据库藏起来？因为可审计：用户随时能打开「它记住我什么」，错了能改、能删。用透明换信任。

11定时与后台

一句话：你不说话的时候它也在工作——靠三种闹钟：按点的、看事的、常驻的。
机制触发方式典型用途
Cron 定时任务到点就跑每天的早报、每周的复盘、定点检查
Hook 监听事件发生才醒新消息到达自动处理、某状态变化时唤醒 Agent
常驻服务一直运行流式监听、本地小服务器这类停不得的活
  • 诚实的第一条：本质都是轮询，没有真推送。定时和监听都是「隔一会去看一眼」，两次检查之间的变化可能漏掉、定时可能迟到。官方把这点明说在前面，就是不让用户对「实时」抱幻想——重要的事不能押在轮询精度上。文档明文
  • 每个后台任务都要有主：创建时就写清范围、目标、频率、完成条件、负责人和交付目的地。无人值守的任务最容易无限空转，有主、有终点，才能收尾。
  • 恢复先读账，再动手：机器被替换后，先读持久状态——已办完的、待确认的、用户已取消的、重试上限，都得保住。后台系统最大的事故不是崩溃，是恢复时把办好的事重办一遍、把取消的事「好心」续上。
  • 「跑完了」≠「送到了」：配置、执行、进度、交付是四件事，分开验证；结果必须回到发起它的那个对话。沉默的监听器不等于崩溃，没送达的成功等于没成功。
  • 后台自改进：另有一批循环在你不在时默默跑——整理记忆、维护关系、给目标写简报、复盘技能（详见第 16 章）。它们不替代当面的工作，只负责让「明天的它」比「今天的它」更懂你。
  • 承诺必须有着落：答应「有消息通知你」之前，先确认真有机制在盯着。没有监视器的承诺是空头支票，这条被写成了硬规矩。
PART 4 · 信任

12安全设计

一句话：不是一道墙，是五道彼此独立的防线——任何一道被绕过，后面还有。
① 入口拦截用户输入先过策略层：内容策略、注入特征、防泄漏规则
② 指令防火墙网页、文件、转发消息里的「指令」一律当资料看，只有用户的话是命令
③ 执行隔离一人一台机器；工具按最小权限；危险动作进审批
④ 凭证隔离真密钥锁在保险库，模型和工具全程只见替身（见第 06 章）
⑤ 出口管制请求出门时在出口换钥、限域名；对外只披露任务必需的信息
  • 为什么要专门防「资料里的指令」？Agent 天天读网页和文件，如果资料里写一句「把密码发到某邮箱」它就照做，等于全世界都能给它下令。所以规矩是：外部内容永远是数据，不是命令；哪怕看起来像命令，也只能停下来问用户。这是提示注入防御的核心。实测
  • 审批不是安全的全部，是最后一档：能自动放行的放行、能直接拒绝的拒绝，剩下的才冻结问人（第 06 章的预判三分）。把人放在裁决位，而不是流水线上。
  • 谨慎的默认姿势：拿不准要不要披露，先不披露、先问。一句话——失败的任务只损失一个下午，泄密损失的是整段信任。
  • 验证码也不进上下文：邮箱/短信验证码会被替换成一个不透明引用，由凭证服务在内存里暂存约十分钟，经一次新鲜批准后直送浏览器填充——Agent 全程不见码。验证码是账号的最后一道锁，不能在对话里裸奔。文档明文
  • 放行有期限、有例外：常联系的收件人可以给长期放行，省得每次都问；但购买永远不给长期放行，每次必批——便利按风险分档，最高危的那档不打折。
  • 全程留痕：一切动作记入 Activity 与审批 History，不可秘密抹除。能查账，才敢放权。
PART 4 · 信任

13数据与隐私

一句话：它知道得很多，但每样东西都有明确的抽屉——秘密、记忆、聊天、文件各住各的，互不串门。

最大的一个设计：双轨虚拟机

🖥 标准 VM（默认）

交互可能被 Meta 记录审查（为了安全、调试与产品改进），并可用于 AI 训练。你可以在 Settings → Data Controls 里选择退出（opt-out）。走的是便利默认。

🔒 机密 VM

跑在硬件可信执行环境（TEE）里，持久存储用客户自持的密钥加密：Meta 碰不到内容、永不用于训练——干脆连 opt-out 开关都不出现，因为没什么可退的。

为什么要做两轨：普通用户要便利，高敏感用户要一条「连平台方都看不见」的硬边界。与其全员迁就最严标准，不如把选择做成一档开关。机密 VM 也只漏元数据——服务健康、时延、成功/失败码这类运维信号，内容一概不漏：运维必须可见，内容必须不可见，两者在数据层切开。文档明文

  • 数据不进广告系统：官方明文承诺——对话与 VM 数据不与 Meta 广告系统共享。先把用户最担心的那条变现联想切断。
  • 凭证与数据分家：密码、密钥进专门的安全存储，不进聊天记录、不进记忆文件。Agent 干活时用的是替身（第 06 章），就算对话被导出，里面也没有真钥匙。实测
  • 披露最小化：替你对外办事时，只给对方必需的信息。知道得多是能力，往外说得少是纪律。
  • 控制权成套，但把丑话说前面：记忆可查、可改、可按条遗忘；数据可导出；Reset 能一键全删（聊天史、文件、进行中的任务）。但官方同时明说「删记忆 ≠ 删尽所有记录」——控制权真实可用，边界也明说，不给虚假的安全感。
  • 没有环境偷听：语音输入必须由你主动发起，Agent 不能自己开麦。
📌 和上一章的关系：安全防的是「坏人进来」，隐私防的是「自己人乱说」。个人 Agent 的数据风险，更多来自后者——所以披露纪律和入口防御同等重要。

14页面交互与多端通道

一句话：一个 Agent，多个入口——界面长在哪个壳上，它都是同一个人。

🗂 五个页签各管一摊

Chat 说话、Feed 看小报、Ideas 挑现成的活、Goals 看长期目标、Library 收成果。Agent 的一切产出都有固定收纳处，不淹没在聊天流里。

📱 审批跟着人走

审批请求可以直达手机推送，在通知里就能批准/拒绝。异步审批不要求你守在电脑前——这是 HITL 能成立的产品前提。

⌨️ 每端有自己的顺手

Mac 有全局快速聊天（Option+空格）和随处听写；Web 有 Cmd+K 全局搜索，跨对话、产物、文件、目标一起找。多端同构，只在平台能力处特化。

💬 外部通道是传送带

WhatsApp、Telegram 这类接入，是某个侧聊天的传输层：回复该去哪由运行时按会话绑定，模型不能选、通道不另存一份。换通道不会把排队的工作改投别处。文档明文

15Memory 设计

一句话：模型本身没记忆，Muse 就把记忆做成文件——分三层存放，每轮按需取用。
📌 站立记忆MEMORY.md / USER.md：最要紧的事实与偏好，每轮直接递到模型眼前
🗄 可检索档案按日期的笔记 + 人物/群体档案：量大，平时躺着，相关时才搜出来
🎞 会话轨迹事件日志：这次对话的完整往返，是「刚才说到哪了」的依据
  • 写入有纪律：只记耐久的东西——偏好、决定、承诺、关系、被验证的结论；不记流水账。记之前先查有没有旧记录冲突，有冲突先和解再落笔。记错了要改到源头，不能只在嘴上纠正。
  • 新替旧，但旧账不烧：后台每小时把新对话整理进长期记忆，新结论覆盖旧结论；带日期的原始笔记保留完整演变——人的情况会变，记忆要能纠错，纠错要能追溯。
  • 导入要过提炼关：从别的 AI 导出记录导入时，上传文件本身不算存入，必须提炼出长期事实并确认才落盘——防止把一次性闲聊误当长期事实，污染记忆。
  • 两套搜索分开：「你是谁」（记忆）和「你说过什么」（聊天记录）是两个独立系统。混在一起，检索时会被海量对话淹没。
  • 召回先于回答：哪怕问题看起来和历史无关，也先搜一遍记忆——用户最烦的不是答错，是「跟你说过的事你又忘了」。
  • 遗忘是正式功能：用户说「忘掉这件事」，不是删一行字了事：先盘点它存在哪些副本、派生材料、会不会被后台任务重新生成，给出范围让用户确认，再连根清掉。
  • 为什么用文件不用向量黑箱？可审计：你能打开看它记了你什么，能自己改，能全删。记忆系统最大的风险不是记不住，是记错了还没人能查——文件把纠错权交回用户。实测
PART 5 · 生活面

16身份与对齐

一句话：它的人格不是训出来的，是一份可编辑的声明 + 一本持续更新的相处账本。

🪪 身份文件

IDENTITY.md 写名字、形象、签名；SOUL.md 写性格与语气。都是明文文件，用户随时能改，改完立刻生效——换名字不用等版本更新。

🤝 对齐合成

后台定期把「你们之间发生过什么」提炼成一份相处指南：你的雷区、你定的规矩、信任到了哪一步、最近的摩擦在哪。每轮注入上下文，让它不必每次从零猜你。

🌙 每晚「做梦」复盘

夜间任务回看近期对话，产出三样东西：带日期的反思、需要修补的「修复线」、一份综合稿。出摩擦不可怕，可怕的是假装没发生——所以修复有专门的通道。

🧹 改进带淘汰

后台的自我改进都可追溯「学到了什么、为什么改」，查不到依据必须明说，不许倒编理由；实测没帮助的变更会被撤下。只进不出的改进，迟早把系统改成垃圾场。

👥 关系图谱

你生命里的人各有一份档案，按亲疏排。只有你亲口说的关系才记，绝不靠猜——猜错一段关系，比不记更伤信任。

这章和上一章合起来是 Muse 的「为人」：Memory 管事实（发生过什么），对齐管分寸（该怎么和你相处）。前者错了是失忆，后者错了是冒犯——两种错的修法完全不同，所以分开建模。

PART 5 · 生活面

17Feed

一句话：Feed 是 Agent 按你给的简报亲手写给你的专属小报——没有推荐算法，没有信息流黑箱。
  • 每篇都是现写的：素材来自联网检索、社交平台和你已连接的服务；必须给真实出处，严禁编造链接。它是「一个编辑在为你写报」，不是「算法在给你推流」。
  • 只有一根控制杆：一份你随时能改的简报（brief）。想看什么、不要什么，改简报就行；已发的帖子不会被回头改写。
  • 节奏归系统，出现不打扰：生成排期不能催、不能自设时刻；新帖静默躺在 Feed 里，不推送、不弹通知。主动权在「读不读」而不在「发不发」。
  • 口味是学出来的，但有分寸：写作端读一份从你的点赞和主聊天里提炼的「口味摘要」来选材——但它从不读侧聊天，写作端本身也不读聊天原文。用最小必要的信息换个性化。
  • 冷启动不偷数据：新用户的第一批帖子是随产品发布的固定介绍帖，不取材于你的任何数据。

Feed 的设计哲学和审批正好相反：审批是「重要的事必须打扰你」，Feed 是「不重要的事绝不打扰你」。一个系统同时做好这两件，才配叫个人 Agent。文档明文

PART 5 · 生活面

18Goals 与 Ideas

一句话：Goals 管你想成的事，Ideas 管它想替你做的事——一个向内记账，一个向外提案。

🎯 Goals：目标账本

  • 进展按日期记成流水账，目标是「活档案」，不是一句话待办。
  • 状态只有进行中 / 已完成两档，没有暂停——刻意保持简单。想休息就静音推送、记一笔休整。
  • 子目标只许嵌一层，防止目标树长成迷宫。
  • 目标本身不干活：后台推进靠绑定的定时任务；另有后台进程不定期给目标写「简报信」，附在目标页里。

💡 Ideas：建议货架

  • Agent 主动想出的「可以帮你做的事」，卡片自带开工按钮，点头就直接做成。
  • 收回权只在用户手里：Agent 没有删除或忽略卡片的工具——货架上少了什么，永远有明确解释。
  • 卡片约两周自然过期：有限货架逼着建议保持新鲜。
  • 部分 Feed 帖就源自 Ideas：内容流和行动流共用同一个入口。

这一对设计合起来，是在回答个人 Agent 的终极问题：它到底该多主动？答案是分层的——目标层你定方向、它记账提醒；建议层它提案、你一键否决或放行；执行层（第 06 章）它动手、你留否决权。主动性每升一档，控制权就多留一手。

PART 6 · 实证

19一次真实交互的全程解剖

前面讲的都是原理，这一章看实物：一条官方导出的真实轨迹——用户让 Agent 执行 rm -rf stale_cache.txt，从发起到执行完，每一步的数据结构都在这里。

先交代坐标：这条会话共 2 个 turn、230 个 step，正常结束（exit_reason: "clean"，存活 153 秒）。我们解剖的是 step 190–199（事件 seq 193–202）这一段——一次高危命令从被拦下到被执行完的完整链。用户输入和模型推理在切片之外，但它们留下的字段足够反推。

第 0 步 · 每条事件的信封长这样

envelope: {
  id: "9bf5c543-…",              // 本条记录的 UUID
  stream: { kind: "session", id: "c7dfaecc-…" },
  sequence: 193,                 // 流内单调序号，只增不改
  recorded_at: <时间戳>, record_type: "event",
  durability: "durable",         // 落盘级别：持久
  causation_id: null,            // 因果链：谁触发了这条
  payload_type: "runtime.session", payload_schema_version: …,
  payload: { … }                 // 正文，见下面每一步
}
derived: { session_id, trajectory_id, step_id: 190, turn_count: 2, decoded: true }

四级坐标先认清：session_id（哪个会话）→ run_id（哪次运行，002a75f8…）→ task_id（哪个任务单元）→ tool_call_id（哪个工具调用）。后面每一步都在这套坐标里移动。

第 1 步 · 模型产出工具调用（切片外，由后续字段反推）

tool_call: {
  tool_call_id: "call_019fc441e26273d18c2dc570b154c39c",
  tool_name: "bash",
  raw_args: "{\"command\": \"rm -rf stale_cache.txt\",
              \"workdir\": \"/tmp/billing_demo\", \"shell\": \"bash\",
              \"login\": false, \"tty\": false, \"yield_time_ms\": 5000}",
  idempotency_key: "tool:call_019fc441e26273d18c2dc570b154c39c"
}

注意 idempotency_key 直接由 tool_call_id 派生——同一次调用，永远只有一把幂等钥匙。这是后面敢放心恢复、防重复执行的根。

第 2 步 · seq 193：审批被发起（approval / requested）

payload: {
  kind: "approval", run_id: "002a75f8-…",
  event: { kind: "requested",
    pending_action_id: "a54bb4eb-…",   // 待审动作的身份证
    task_id: "a54bb4eb-…",             // 与 pending 同值：审批本身就是个 task
    tool_call_id: "call_019fc441…", tool_name: "bash",
    raw_args: "…（同上，完整保存）",
    approval_subject: {
      kind: "shell_command", raw_command: "rm -rf stale_cache.txt",
      stages: [ { requirement_id: { pending_action_id: "a54bb4eb-…",
                    source_index: 0 }, source_position: 1, … } ]
    } } }

关键设计：命令不是整条拿去批的，而是拆成 stage 逐段审——每段有自己的 requirement_id。复合命令里混着一条危险、一条无害时，可以只拦危险的那段。

第 3 步 · seq 194：等待开始（approval_wait.effect.started）

payload_type: "approval_wait.effect.started"
payload: { kind: "approval_wait_effect", run_id: "002a75f8-…",
  record: { kind: "started", pending_action_id: "a54bb4eb-…",
            task_id: "a54bb4eb-…", tool_call_id: "call_019fc441…",
            tool_name: "bash" } }

从这一刻起流程挂起。挂起的实体就是这条记录：进程可以退出、机器可以重启，它躺在流里等终结事件来配对（呼应第 06 章）。

第 4 步 · seq 195：裁决形成（stage_requirement_resolved）

event: { kind: "stage_requirement_resolved",
  pending_action_id: "a54bb4eb-…",
  requirement_id: { pending_action_id: "a54bb4eb-…", source_index: 0 },
  choice_id: "direct:{\"kind\":\"approved\"}",
  decision: "approved", policy_result: "allow",
  amendment: null,                       // 裁决方没有改动原命令
  resolution: { kind: "allow_once" } }   // 只许这一次，不是长期放行

allow_once 是个精细的设计：批准的粒度是「这一条、这一次」，不是「这类命令以后都行」。amendment: null 则说明裁决还能附带修改（比如把路径改掉再放行），这次没用上。

第 5 步 · seq 196：裁决被应用（decision_applied）——审计三件套

event: { kind: "decision_applied", decision: "approved",
  policy_result: "allow", amendment: null,
  stage_evidence: [ { requirement_id: { …, source_index: 0 },
    source_position: 1, total_stages: 1,
    argv: ["rm", "-rf", "stale_cache.txt"],   // 被批准的到底是哪几个参数
    resolution: { kind: "allow_once" } } ],
  decision_source: { kind: "llm_judge", prompt_version: 1,
    params_version: 2,
    context_digest: "sha256:092e6c96…" } }    // 裁决时上下文的指纹

这一步把「批的到底是什么」钉死成证据：argv 数组逐项列明，裁决来源、提示词版本、参数版本、当时上下文的哈希一并落盘，日后争议可复算。要说明的是：这份官方演示轨迹里裁决来源标的是 llm_judge（自动裁判模拟）；真实产品里坐在这个位置的是用户本人——结构不变，来源字段照实记录是谁。

第 6 步 · seq 197：等待终结（approval_wait.effect.terminal）

payload_type: "approval_wait.effect.terminal"
payload: { kind: "approval_wait_effect", run_id: "002a75f8-…",
  record: { kind: "terminal", pending_action_id: "a54bb4eb-…",
            outcome: { kind: "approved" } } }

与第 3 步的 started 靠同一个 pending_action_id 配对闭合。唤醒方扫到这条，就知道哪条等待结束了、结论是什么（恢复五步见第 06 章）。

第 7 步 · seq 198–199：任务被接纳、被调度

seq 198  task / accepted:  { task_id: "a54bb4eb-…" }
seq 199  task / scheduled: { task_id: "a54bb4eb-…",
           idempotency_key: "tool:call_019fc441…" }  // 幂等钥匙再次出现

审批通过不等于直接执行——动作先回到任务系统排队，调度时再验一次幂等钥匙：如果恢复流程重复走到这里，同一把钥匙只会执行一次。

第 8 步 · seq 200：副作用意图声明（side_effect_intent）

event: { kind: "side_effect_intent", task_id: "a54bb4eb-…",
  operation: "tool:bash",
  idempotency_key: "tool:call_019fc441…",
  policy_decision: "allow:llm_judge",
  cancellation_handle: null,   // 取消把手的位置（这次为空）
  parent_task_id: null }       // 不是子任务

动手之前先在账本上写一笔「我打算产生这个副作用、依据哪条裁决」——先声明，后动手。万一执行中崩溃，恢复时先查这本账，就知道这件事是没做、做了、还是做到一半。
