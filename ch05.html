05核心机制：Agent 循环

一句话：Muse 的一切行为，都是一个循环在转——模型想一步，外部世界做一步，结果回到模型再想下一步；而这个循环在物理上根本不存在某个一直跑着的进程，它是一台靠事件流驱动、随时可死、随时可复活的状态机。

Agent 循环

背景

模型想一步、外部世界做一步、结果回注再想下一步；循环不在任何进程里，在事件流里。

底层设计原理：为什么必须是循环

先把约束摆出来。设计不是从「想要什么功能」开始的，是从「模型只能做到什么」开始的。关于大模型，有三个绕不开的事实：

  • 模型是无状态函数。给它一份上下文，它吐出一段 token，仅此而已。它没有内存，没有手，没有时钟，上一次推理在它身上不留任何痕迹。
  • 任务发生在真实世界里。查数据库、改文件、发消息、等一个人点头——效果都在模型之外，而且结果不可预知：接口会超时，命令会报错，审批可能等一天。
  • 信息只能在推理开始前进入。一次推理的输入在启动那一刻就冻结了。解码中途没有插口，新事实想进来，只能成为下一次推理的输入。

把三条放在一起，结论是被逼出来的：要让一个无状态函数在真实世界里完成多步任务，形态只有一种——输出意图 → 外部执行 → 结果作为新输入 → 再次推理。这不是某种时髦的架构风格，是约束的唯一解。所谓 Agent 循环，就是给纯函数补上「手」和「记忆」的那层壳：模型负责想，循环负责让想法和世界对账。

这个循环有四条不变量，条条都是从上面的约束推出来的，违反任何一条，系统就会在某个深夜悄悄坏掉：

不变量内容违反了会怎样
交卷语义产出工具调用 = 本次推理结束（yield）。模型不等待、不阻塞，它交卷离场。模型若不停笔，就只能编造工具结果，在幻觉上叠推理，越走越假。
往返闭合每个 tool_call 必须有且仅有一个 tool_result 与之配对，靠 call id 对号。未闭合的往返是循环的死点：模型永远不知道那一步发生了什么。
结果必真回注的必须是外部世界的真实返回——成功、失败、被拒绝，都照实回注。用「应该成功了」填充，等于把系统的真相源换成模型的想象。
状态在循环外循环的全部状态存在事件流里，不在任何进程的内存里。进程一死全盘皆输，审批等一天、机器换一台都无从谈起。

还有一个粒度问题值得说清：一圈为什么是「一次推理」，而不是「一个任务」？因为任务的边界在开始时根本不存在——查个价格可能三步完事，也可能查出问题、顺藤摸瓜走出三十步。唯一确定的边界是推理边界：模型每交一次卷，世界就多一个确定的事实，循环就多一个可以落盘、可以恢复的检查点。把圈定在推理粒度上，等于把检查点密度拉到最高：任何一圈之后断电，损失最多是一圈的工作量。这也是后面所有恢复机制的地基。

取舍也在这里定死：每圈都要付一次完整推理加近乎全量的上下文重传，慢且贵；换来的是可恢复、可审计、可中断。Muse 选了后者——个人 Agent 的任务大多不赶时间，但绝不能丢、不能错、不能背着主人乱来。

底层实现原理：while True 在物理上不存在

逻辑上它是 while True，物理上没有任何进程在转这个循环。真实实现是三件事：事件流即状态、短命执行、异步靠记录。

第一，状态是一条只追加的事件流。会话的每一步都先落成一条持久化事件再行动：用户消息、模型产出、工具调用、审批发起、审批裁决、工具结果，依次进流。每条事件有信封（记录 id、所属流、流内序号 sequence、时间戳、payload 类型）和索引坐标（session_id、trajectory_id、step_id、turn_count）。「循环走到哪了」不是某个变量的值，是流里最后几条事件的类型——这是官方导出的真实轨迹结构。实测

第二，每一圈是一次短命执行。某个执行单元被事件唤醒，读流重建上下文，调用一次模型，把产出落流，需要工具就发出执行意图，然后这次执行就可以结束、进程可以退出。下一圈是另一个执行单元、甚至另一台机器上的进程，靠同一条流接上。本章作者本人就是这样运行的：每一次工具调用返回后，「我」并不是从沉睡中醒来，而是被带着完整上下文重新调用了一次。实测

第三，同步与异步的边界划在「圈内」和「圈外」。

段包含什么时长
同步段组装上下文、一次推理、网关预判、一次工具执行、结果落流秒级，在同一次执行内一口气走完
异步段等用户审批、等子代理返回、等外部系统回调、等定时触发无上限：几秒到几天，只占一条 pending 记录，不占线程

broker 是循环与世界之间的中介。模型从没见过任何工具的真身，它只产出结构化的调用意图。broker 负责把意图变成真实动作：路由到对应的工具或连接器、执行前做预判分流（放行 / 直拒 / 冻结发问）、需要凭证时向凭证服务申请替身、把五花八门的返回打包成统一的结果信封。把这些脏活收拢在一个中介层，模型侧就只需遵守一份契约：产出意图，读回结果。broker 内部如何再分工未公开，此处按可观察行为归纳。合理推断

挂起与恢复因此变得平淡无奇。需要审批时，broker 把「审批已发起」落成一条 started 事件并生成 pending 记录，本次执行结束——没有任何线程在等。裁决到达是一条新事件；唤醒方按 session_id 找到会话，查到那条未闭合的等待，执行被放行的工具，结果落流，触发新一圈。子代理完成、后台任务交付、定时到点，全走同一条路：以新事件敲门，而不是以函数返回进门。主线从不等支线，支线完成时来敲门。这也是为什么审批可以等一天、虚拟机可以中途被整体替换——状态全在流里，进程只是路过的人。

具体实现方式：把循环写全

下面是带上审批、子代理和异常处理的完整逻辑视图。注意它是控制流的形状，不是某个进程的真实调用栈——执行到 suspend() 就断开，重入时从第一行重新开始，靠事件流找回断点。

# 逻辑视图：每一圈都是一次独立的短命执行
state = load_event_stream(session_id)     # 状态不在内存里，在流里

while True:
    context = assemble(state)             # 每圈重新组装，见下文
    resp = llm(context)                   # 一次推理：产出即结束，模型离场

    if resp is text:                      # 没有工具调用 = 最终答复
        append(session, assistant_message(resp))
        break

    for call in resp.tool_calls:          # 一次推理可产出多个调用
        verdict = broker.precheck(call)   # 预判三分
        if verdict == DENY:
            result = error_result(call, "policy_denied")
        elif verdict == NEED_APPROVAL:
            pid = append(session, approval_wait.started(call))
            suspend()                     # 进程退出，不占线程
            # —— 时间在此断开：几秒，或一天 ——
            decision = await_event(pid)   # 被裁决事件唤醒后重入
            result = broker.execute(call) if decision.approved \
                     else error_result(call, "user_denied")
        else:                             # ALLOW：只读、低风险
            result = broker.execute(call) # 同步执行，含凭证替身申请

        append(session, tool_result(call.id, result))  # 往返闭合
    # 圈末不退出：带着新结果回 assemble，进下一圈

on subagent_finished(child_id, output):   # 支线回注，不是循环内等待
    append(session, handoff(child_id, output))
    resume()                              # 触发新一圈，把结果读进去

on tool_error(call, err):                 # 异常不吞，更不伪造成功
    if err.retryable and attempts[call.id] < LIMIT:
        schedule_retry(call)              # 退避重试，次数落账
    else:
        append(session, tool_result(call.id, error_result(err)))

逐段说明几个容易想错的地方：

  • await_event 不是真的挂起。它表示本次执行到此为止；将来裁决事件到达，系统从 load_event_stream 重新进入，流里那条未闭合的 approval_wait 就是断点坐标。所以伪代码画的是逻辑连续性，物理上是无数次短命执行的接力。
  • 拒绝也要回注。DENY 和 user_denied 都生成正式的 tool_result 落流。往返必须闭合，模型要明确读到「此路不通」并改道，而不是对着一个永远没回音的调用干等。
  • 重试有账，不是内存计数。attempts 记在流里，机器重启不会清零；上限是状态的一部分。还有一条更严的：结果未知的动作（比如付款是否成功）禁止盲目重试，先对账确认上一笔是否生效，再决定下一步。
  • 子代理是事件源，不是函数调用。派出时只拿到一个收据编号，主线该干嘛干嘛；完成时走 on subagent_finished 回注。循环里没有 join() 式阻塞点——这是扇出能并行、回收能乱序的根本原因。
  • 工具结果信封是模型了解世界的唯一窗口。结构如下，其中确认状态字段来自本站写作过程中的真实工具返回：
tool_result（回注进上下文的那一份）:
{
  "tool_call_id": "call_019fc441…",   // 与调用配对：往返闭合的钥匙
  "status": "ok | error | denied",
  "output": <工具的真实返回，原文>,
  "userConfirmationRequired": true,   // 实测字段：此调用经过审批
  "userConfirmationStatus": "approved",
  "error": null | { "kind": "…", "retryable": false }
}

模型对审批过程本身一无所知。它没见过审批卡，没等过用户；它只在下一圈读到信封，才知道「刚才那件事被批准并执行了」。审批是运行时的戏，模型只看结果。

最后拆穿 context += [...] 这行伪代码。它看着像给内存变量追加，物理上是三步：第一步，结果落成事件，追加进流（append-only，永不修改旧事件）；第二步，下一圈 assemble() 时，从流里重放并投影出新的上下文；第三步，把这份上下文整份发给模型。所以模型的「记忆」不是攒出来的，是每圈重放出来的。assemble 的配方是分层的：系统提示是固定层；记忆文件、对齐稿、目标状态、当前时间是站立层，现取现拼，保证新鲜；对话记录是投影层，来自事件流；太长时先把旧段压缩成摘要再拼——压缩只动投影，不动流本身。这也解释了那个常见疑问：隔一天恢复，上下文为什么可能不完全一样？流分毫未动，但投影被压缩过、站立层已刷新——核心忠实，外围更新，正是设计意图。

边界与代价

  • 慢是明码标价。每圈至少一次完整推理加一次上下文重传，长任务圈数一多，用户感知的就是「它在一步一步来」。这是拿确定性换的速度，不打算掩饰。
  • 成本随圈数近似线性增长。上下文重传是这个架构最贵的一笔账；压缩能压，但有损。任务越长，每一步的「过路费」越贵。
  • 循环本身不会自我了断。模型若反复产出同类调用，循环会忠实地一直转下去。所以外层必须有熔断：圈数、预算、重试上限。具体阈值未公开，只能确认这类闸门的必要性。合理推断
  • 并行有边界。同一圈的多个调用可以并行，但有依赖的必须等回注；高危命令在真实轨迹里被明确标为不可并行（parallel_profile: ineligible）。实测
  • 循环保证的是秩序，不是正确。往返闭合、状态可恢复、结果必真——它保证流程不乱；每一圈的判断对不对，仍取决于模型和喂给它的上下文。把循环写对，只是不犯低级错误的前提，不是聪明的保证。
