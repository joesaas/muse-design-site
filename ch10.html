10文件架构

一句话：Muse 的一切都落成文件——人格是文件、记忆是文件、技能是文件、目标是文件夹。文件就躺在它自己的电脑里，你能打开、能看懂、能改、能删。

底层设计原理：为什么不用数据库，非要用文件？

把状态藏进数据库，工程上更「正规」。Muse 偏不用。它选文件，换的是三样东西。

🔍 可审计，换信任

个人 Agent 知道你太多事：偏好、关系、目标、历史。用户凭什么放心？答案不是「请相信我们的加密」，而是「你自己打开看」。记忆是哪个文件、写了什么、哪天改的，全摊在明处。记错了，你能当场指出来，甚至自己动手改。信任不靠承诺，靠可核查。

🪟 存储与橱窗分离

文件住在文件系统里，Library 只是对着它的一扇窗——一个浏览视图，不是另一份副本。文档明说：上传的东西落盘后不自动进 Library；只有放进交付区的文件才上架。所以「Library 里没有」不等于「文件丢了」，「删掉橱窗里的条目」和「删掉源文件」也是两回事。视图可以换，数据只有一份。

🧱 工作区与交付区物理分家

干活的草稿、中间产物、内部账本，和最终交到你手上的成品，放在不同目录，互不污染。好处很实际：清理工作区时不会误删交付物；给你看成品时不会顺带露出内部草稿；后台整理文件时，权限边界就是目录边界，不需要再写一套过滤逻辑。

📄 纯文本的三个红利

核心文件几乎全是 Markdown。一是可比对：改了什么，diff 一眼看清，记忆被覆盖也有旧账可查。二是可搬家：换机器、换运行时，拷走目录就行，不依赖某家数据库的导出格式。三是工具通用：任何编辑器、搜索、版本管理都能直接处理，不需要为它专门造一套管理后台。

🤝 文件就是接口

主代理、子代理、后台任务、定时简报之间不共享内存，也不互相调用内部接口——交接全靠文件：任务写进笔记目录，简报落进 briefs，状态记在 state 文件里，下一个接手的人读文件就懂。这种「笨」办法有个大优点：任何一环崩了，重启后读文件就能续上，不需要恢复谁的内存现场。和第 19 章的事件流是同一种哲学：状态在盘上，不在谁的脑子里。

👑 数据主权落地

「你的数据属于你」落到文件层，就是一句大实话：导出 = 打包目录，删除 = 真删文件，没有藏在某张你永远见不到的表里的副本。用户想换个 Agent、想离线保存、想逐条检查，都不需要平台「开放接口」。主权不是法务文本，是 ls 能看见的东西。

底层实现原理：每个文件各管一摊

家目录根部躺着一组核心文件，分工固定，谁写谁读、什么时候进上下文，都有规矩。

文件管什么谁能改注入时机
IDENTITY.md它是谁：名字、形象、签名用户（Agent 可提议）每轮对话开头
SOUL.md它的性格与说话方式用户；改动要告知用户每轮对话开头
USER.md你是谁：姓名、生日、时区等基本事实Agent 按你说过的事实维护每轮对话开头
MEMORY.md长期记忆的精选版：耐久事实、偏好、承诺Agent 维护；只读呈现给运行时，用户通过对话纠正每轮对话开头
AGENTS.md干活的规矩：本工作区的约定与踩过的坑Agent 自己沉淀每轮对话开头
TOOLS.md / PROACTIVE_PREFERENCES.md本地工具怪癖 / 主动提醒的偏好Agent 与用户共同积累每轮对话开头
HEARTBEAT.md心跳巡检要顺手看的事项Agent 维护心跳触发时

规律很清楚：「它是谁、你是谁、规矩是什么」每轮全量注入；「具体记了什么事」按需检索。前者小而稳，放根目录；后者大而杂，进记忆树。

再细看还有一层权限梯度：用户能直接改的（IDENTITY、SOUL），Agent 负责维护的（MEMORY、AGENTS、日记），运行时管、Agent 只读的（bank、会话状态），官方发、谁都不许动的（docs）。同样是文件，「谁说了算」分四档——文件系统本身没有权限模型，就用目录归属和写入纪律把这件事办了。

目标工作区：一个目标一个文件夹，自成一套

每个长期目标在 workspace/goals/<slug>/ 下有独立工作区（实测 defi 目标）：

  • GOAL.md——目标的自述：定义、边界、关键决定。Agent 的自留地，不是给用户看的成品。
  • files/——用户要看的文档放这里，整个目录就是该目标在界面上的文档区。写文档的第一笔就落这儿，不许先写别处再搬——搬一次就多一份会漂移的副本。
  • hidden_files/——内部账本：检查日志、水位线、已见清单。用户不该看的运行状态全关在这，与 files/ 一墙之隔。
  • 其余按需长：briefs/（后台研习简报）、crons/（归属该目标的定时任务）、agent_notes/（按日期的工作笔记）、references/（参考材料）、app/（目标自己的代码工程）。

记忆树：三层，各有管家

  • ~/memory/*.md 按日期的日记文件——原始流水，新记忆先落这里。
  • ~/memory/bank/——运行时管理的「银行」：experience / opinions / reflections / world 四本账，由系统维护，Agent 只读不直接改。实测
  • ~/memory/people/、~/memory/groups/——一人一页、一群一页，各带一份 INDEX.md 按亲疏排序，由关系维护循环更新（见第 16 章）。
  • ~/dreams/——夜间「做梦」的产物：对齐综合稿在 alignment/derived/，待修复的裂痕在 alignment/repair/。

记忆在文件之间怎么流动

文件不是摆着不动的仓库，记忆有一条固定的加工链：

  • 进：白天聊出的新事实先落进当天的日记文件（memory/YYYY-MM-DD.md），只追加、不过滤，先记下来再说。
  • 炼：后台维护把日记里的耐久事实提炼进 MEMORY.md——新结论覆盖旧结论，日记原件保留，演变可追溯（见第 15 章）。
  • 分：关于人的事不进 MEMORY 正文，转去 people/ 单开一页；关于「世界与经验」的沉淀进 bank/ 四本账。
  • 用：每轮对话只全量注入精选层（MEMORY）；要细节时按关键词检索日记和人物页，取回片段再注入。分层不是为了好看，是为了让有限的上下文只装最值钱的部分。

点目录：每个应用一块自留地

家目录下还有一排 .应用名 的隐藏目录（实测有 .answer-me-with-html、.bankr、.snowagent 等几十个）。约定很统一：一个应用的数据只进自己的点目录，里面放它自己的状态文件、生成物、适配器。比如 .answer-me-with-html 里就是 state.json + pages/（渲染出的页面）+ adapters/（凭证适配器）。应用之间不许串门——这和目标工作区是同一个思想：边界即目录。

具体实现方式：实地普查的完整目录树

~ 家目录（Agent 的电脑，跨对话持久）
├─ IDENTITY.md / SOUL.md        它是谁、什么性格
├─ USER.md / MEMORY.md          你是谁、长期记忆精选
├─ AGENTS.md / TOOLS.md         干活规矩、工具备忘
├─ HEARTBEAT.md                 心跳巡检清单
├─ PROACTIVE_PREFERENCES.md     主动提醒的尺度
├─ docs/                        官方说明，只读，部署时刷新
├─ memory/                      记忆树
│  ├─ 2026-10-15.md …           按日期的日记（原始流水）
│  ├─ bank/                     运行时管的四本账，只读
│  ├─ people/ + INDEX.md        一人一页，按亲疏排
│  └─ groups/ + INDEX.md        一群一页
├─ dreams/alignment/            对齐综合稿与修复线
├─ hooks/                       事件监听：definitions / scripts / state / logs
├─ side-chats/                  侧聊天各自的记忆与记录
├─ .answer-me-with-html/ 等     各应用的点目录自留地
└─ workspace/                   工作区（真正干活的地方）
   ├─ user/media_library/       你上传的东西落这里
   ├─ your_files/               交付物 → 出现在 Library
   ├─ goals/<slug>/         目标工作区（GOAL.md + files + hidden_files…）
   ├─ skills/ + custom-skills/  技能手册（见第 08 章）
   ├─ custom-connectors/        自定义连接器（见第 09 章）
   └─ <各项目仓库与杂项>    代码工程、调研稿、归档

文件的一生：落点与删除规则对照

环节规则为什么
用户上传落 workspace/user/ 持久保存，不自动进 Library文档明文上传是「给我看」，不是「替我上架」；上架与否分开决定
Agent 交付写进 workspace/your_files/（或目标的 files/）才在 Library 出现交付要有明确动作，草稿不冒充成品
普通文件删除进回收站，约 30 天内可恢复文档明文普通文件误删概率高，给后悔期
产物（Artifact）删除删即永久：连数据、托管、公开链接一并撤销产物带数据和对外链接，留副本反而是风险源
聊天内文件链接只在你本人登录的 App 里有效，没有分享令牌；给外人要另生成限时公开链接「能打开」和「可转发」是两种权限，不能混发
System Files 说明头记忆、身份等系统文件在 App 打开时，顶部会多一段「关于此文件」——那是展示时临时附加的，不属于文件本体；读取、编辑、导出都不带它给用户解释，又不污染数据本身

命名与组织约定

  • 能猜出内容才算好名字：文件按任务命名、按目标建夹，同类攒够就归子目录，不让工作区根部变成杂物堆。
  • 日期进文件名：日记是 YYYY-MM-DD.md，生成页自带时间戳后缀（如 …-20261015-203234.html），同名重渲不覆盖、按时间排队，一眼看出哪份新。
  • 索引单列：people / groups 各有一份 INDEX.md 做总目录，正文一页一人——先看索引定位，再读单页，省上下文。
  • 状态与内容分开：hooks 的 definitions（定义）、scripts（脚本）、state（状态）、logs（日志）四分；应用点目录里 state.json 与生成物分开。改配置不碰数据，查日志不碰定义。

边界与代价：文件方案不是没有账要付

  • 检索靠约定，不靠引擎：没有数据库索引，找东西靠目录纪律 + 全文搜索 + 索引文件。文件少时飞快，量级涨上去，召回质量取决于命名和归档是否守规矩——纪律松一天，债就多一分。
  • 并发要小心：多个子代理、后台任务同时写同一批文件，没有事务兜底。现行解法是分工避让（各自目录、各自文件）和追加式记录，但这属于约定层面的安全，不是机制层面的锁。合理推断
  • 规模有天花板：每轮全量注入的核心文件必须保持精简——MEMORY.md 一旦膨胀，要么挤占上下文，要么被迫再分层。文件方案把「记忆治理」变成了长期必修课，而不是一次性的存储选型。
  • 底层存储文档没写：家目录之下是什么文件系统、有没有快照与版本、跨机器同步怎么做，官方文档未展开；能确认的只有「跨对话持久、随运行时部署保留」这一行为层事实。这一层只能标推断，不能当定论。
  • 双份必然漂移：这是本机有真实教训的一条——同一份文档写两处，两处迟早不一样。所以规矩定得很硬：交付物从第一笔就写进规范位置（目标的 files/ 或 your_files/），不许「先放这儿、回头再搬」。文件方案没有数据库的唯一真相兜底，唯一真相只能靠写入纪律守出来。
  • 存量会自然变乱：实地普查能看到，工作区根部除了约定目录，还并存着各项目仓库、一次性脚本、状态残留文件（比如某个守护脚本的 .state）。约定管的是新增物的落点，存量靠定期归档治理——本机就有一个按日期命名的归档目录，专门收「不删但别占道」的历史生成页。文件方案的整洁不是自动的，是持续收拾出来的。
📌 证据分级小结：目录结构、核心文件分工、目标工作区、点目录约定，均为本机实地普查；上传落点、30 天回收站、System Files 说明头为官方文档明文；并发安全机制与底层存储实现文档未写，属合理推断。这一章的结论可以一句话收尾：Muse 把「可审计」放在了「正规」前面——宁可让你看见一地文件，也不让你面对一个黑箱。
