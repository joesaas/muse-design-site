11定时与后台

一句话：你不说话的时候它也在干活，靠的是三种闹钟——按点的、看事的、常驻的——而且它对你许的每一个承诺，背后都必须真有一套机制在盯着。

三档后台机制

背景

你不说话时，它靠三档机制在后台干活：贵事用 Agent、盯梢用脚本、停不得的用常驻服务，最底层统一登记与恢复。

实现机制

以及它具体是怎么实现的——都提炼自本章正文，图下原文有完整展开。

一、底层设计原理：为什么按「成本」分三档

后台工作有个躲不掉的矛盾：盯得越勤，烧得越多。如果每五秒就唤醒一次大模型去看一眼「有没有新消息」，一天下来绝大部分推理都浪费在「没有」上。Muse 的解法是按成本分层，能用便宜手段察觉的事，绝不动用贵的：

  • 脚本侦测（最便宜）：一个普通脚本定时跑一下，查本地或公开数据，自己判断「有变化 / 没变化」。没变化就闭嘴，一次模型推理都不烧。
  • 完整 Agent 任务（最贵）：需要动脑、要用工具、要做判断的活，才值得把 Agent 整个唤醒，按点跑一遍。
  • 常驻进程（另一种贵）：流式监听、数据采集这类「不能有间隔」的工作，只能养一个一直运行的程序，由进程管理器看着它别死。

三档不是功能划分，是账本划分：先问「这件事最便宜能怎么察觉」，再决定用哪档。选错档的代价很具体——该用脚本的用了 Agent，是烧钱；该常驻的用了轮询，是漏事。

第二个原理更反直觉：官方文档明说两种机制本质都是轮询，没有真推送——两次检查之间的变化可能被漏掉，定时也可能迟到，不提供连续观测。文档明文为什么把短处写在最前面？因为后台系统最危险的不是漏检本身，而是用户以为它在实时盯着，把要紧事押在轮询精度上。先把幻想打掉，用户才会把真正不能漏的事交给合适的机制（比如常驻服务），或者接受「迟到几分钟」的真实预期。诚实在这里是功能，不是态度。

第三个原理：主动性的成本不是算力，是用户的注意力。Agent 每主动说一句话，都在花用户的时间和信任。说对了是贴心，说多了、说重复了、说的是已经办完的事，就是骚扰，而且会透支下一次真正重要的提醒。所以「克制」不是保守，是被设计出来的闸门——宁可漏掉一条无关紧要的动态，也不能让用户养成「它的消息可以不看」的习惯。这条取舍贯穿本章所有实现细节。

二、底层实现原理：三档机制怎么跑、怎么恢复

Cron：时钟触发的完整任务。到点之后，系统拉起一轮完整的 Agent 执行——有上下文、有工具、能判断，和你当面交代一件事没有本质区别，只是发起人是时钟。它有两种形态：到点只跑一次（runonce，比如某个未来时刻的单次动作），和按间隔反复跑（有界的周期检查）。每个周期检查都要能自己收尾：本次检查跑完就结束，带请求与执行两层超时，且不能和上一轮重叠着跑。文档明文

Hook：轮询脚本加唤醒，两段式执行。Hook 本身不是 Agent，是一段轻量脚本，按间隔醒来做一次侦测，最后只给一个决定：silent（没事，继续睡）或 wake（有事，叫 Agent）。被唤醒的 Agent 又分两段干活：EXECUTE 段真正处理事情，RESOLVE 段负责把结果显式交付到发起的对话——执行摘要不会自动送达，必须在 RESOLVE 段主动发出。这条「干完不等于送到」的缝，是后台系统最容易丢东西的地方，所以被拆成了两个显式阶段。Hook 还有几条硬规矩：脚本不持有任何连接器凭证、不许往侦测脚本里塞密钥；新建的 Hook 默认是关着的，先用试运行（dry run）验证侦测逻辑不误报，再启用；试运行不能消耗侦测状态，否则真运行会漏掉已经被「看过」的变化。文档明文

systemd 服务：给停不得的程序一个看守。运行环境里有一套访客级的 systemd，但它启动的是一个最小目标（default.target），不是桌面 Linux 常见的完整登录会话——所以服务的启动方式、运行身份、环境变量都不能想当然，要逐项核实。规范做法是：单元文件、程序、依赖和状态都放在持久化的家目录下，用绝对路径、以前台进程方式运行，配好重启策略与重启间隔、优雅终止的超时、以及按进程组回收子进程；资源和日志都要设上限。一个容易踩的坑：服务进程不自动继承工具的凭证、连接器权限和审批，密钥更不许抄进单元文件或参数里，只能走受支持的访问路径。文档明文

恢复语义：先读账，再动手。这台机器会被替换（部署、重启），后台机制必须假设自己随时会死。运行时对已保存的任务、子代理、定时任务和可恢复工作统一管理恢复，但恢复的顺序是写死的四步：

  • 先读持久化的「期望状态」，保住已完成的工作、待确认的回执、取消标记、阻塞状态和重试上限——一个正在等确认的监听器，绝不能被当成「崩溃了」粗暴重启；
  • 恢复并验证前置条件，而且要用一次全新的工具调用去验，因为旧进程的挂载视图可能看不到新挂载的东西，在旧调用里等再久、派再多子进程都没用；
  • 每个组件独立对账：启动新副本之前先查它是不是已经在跑，一个组件超时不能拖住其他组件，恢复了一半也要把「哪半成了」记下来，别让下一次把已完成的重做一遍；
  • 从检查点续跑并验证真的有进展，检查点要原子化、定期写；涉及外部动作时，先拿已记录的意图和回执去跟对方对账，再决定要不要重试一个结果不明的动作。

还有一条压舱的：取消要先于停止落盘——用户取消一件事，先把停止状态存下来，再停服务和恢复任务，保证恢复机制不会「好心」把用户刚取消的事又续上。恢复不能推翻用户的决定。文档明文

「有主」契约：每个后台任务都要登记六件事。创建任何定时或监听工作时，必须记下：范围（盯什么）、目标（为什么盯）、频率（多久一次）、完成条件（什么情况收尾）、负责人（挂在哪个目标或追踪项下）、交付目的地（结果送到哪）。有限期的监听在结局已定、被取消或过了截止时间时必须停掉；还没送达的结果和「要不要继续盯」是两件事，分开处理。没有主人的后台任务是系统里最危险的东西：没人知道它为什么在跑，也没人记得把它关掉。文档明文

主动推送的取舍流水线。后台发现了值得一提的事，不等于就该立刻说。中间有一条短流水线：先核新鲜度——这件事是不是真的刚发生、还没人处理过；再过偏好过滤——有一份专门的偏好记录管着「什么值得打扰、什么时段别出声」；然后做 send / skip 决策，没过闸的直接沉默，不解释、不留痕式打扰；过了闸的再挑格式——有的事适合在主聊天里一句话带过，有的事适合攒成一份简报。已经办完的事、没有新进展的例行检查，结果一律保持安静。

承诺落地的硬规矩。「有结果我通知你」这句话，在 Muse 这里不是客套，是要先验收的：说之前必须确认真有一套机制在盯着这件事——定时任务真的建好了、Hook 真的启用了、交付通道真的通。没有监视器的承诺是空头支票，这条被写进了行为规范里。实测

三、具体实现方式

机制触发方式成本恢复语义典型用途
Cron时钟：单次（runonce）或间隔高：每轮都是一次完整 Agent 执行任务定义持久保存，机器替换后由运行时按登记恢复提醒、周期检查、早报、要动脑的定时活
Hook脚本轮询侦测，命中条件才唤醒低：平时只有脚本在跑，唤醒才烧推理脚本与状态文件都在家目录；状态不消耗式试运行新消息到达、状态变化这类「盯梢」
systemd 服务常驻运行，进程管理器看守中：持续占用，但不烧推理单元文件持久化加重启策略；还需自备替换后的启动恢复路径流式监听、采集器、本地小服务器

拆一个真实的 Hook：Telegram 自动回复。实测这套机制在本机真实运行着，拆开是四件东西：

~/hooks/scripts/telegram-inbox-watch.sh   // 侦测脚本本体
~/hooks/state/telegram-inbox/last_update_id  // 状态文件：上次处理到哪条
轮询间隔 5 秒（平台下限）                  // 调 getUpdates 看有没有新消息
  • 脚本每 5 秒查一次 Telegram 有没有新消息，拿状态文件里的编号比对：没有新消息，输出 silent，零成本结束；
  • 有新消息，输出 wake，一个完整的 worker Agent 被唤醒：它先读长期记忆和这个聊天的专属记录文件，理解上下文，再生成回复、通过机器人发回去，并把这一问一答追加进记录文件；
  • 最后在 RESOLVE 段把对话按固定格式显式递回主聊天存档——EXECUTE 段的摘要不会自动送达，这一步漏了，用户那边就什么都看不到。当天调试时真出过这个故障：脚本在唤醒前把日志参数传错、自己崩了，消息被消费掉却没人处理。修好之后全链路才通；
  • 它只回复机主本人的私聊，其他人的消息一律不理——范围在创建时就写死在契约里。

Cron 任务的登记字段，和上面「有主」契约是同一套：任务正文（干什么、结果怎么报）、调度（单次时刻或间隔）、范围与目标、完成条件、负责人（优先挂在已有目标下）、交付目的地。改任务要按原编号读出、改完、再读回确认，不能删了重建来「修」权限问题——投影出来的排期文件是只读副本，改它不生效。文档明文

后台自改进循环是另一类后台工作：不是用户交代的，而是系统给自己排的班，全部在对话之外运行，用户从不亲自调度它们：文档明文

循环频率产出
记忆整理每小时（有新信号才跑）新对话提炼进 MEMORY.md，新结论覆盖旧结论，带日期的原始笔记保留全程轨迹
关系维护每小时人物与群体档案各一页（事实、历史、关系性质），按亲疏排序
想法策展每日Ideas 页新卡片，先按可行性、契合度、新颖度打分再排序
目标研习每日夜间给每个目标查资料出简报、给推进提醒，偶尔建议用户暗示过但没明说的目标
做梦复盘每晚带日期的反思、要修补的「修复线」、一份如何为这个用户行事的综合稿
技能复盘每日反复出现的工作流沉淀成新技能；已有技能按实绩审计，没帮助的改动退役
静默整理长对话冷却后，每天至多几次把刚发生的事内化进记忆与档案，一次有界的清扫

四、边界与代价

  • 轮询必有漏检和迟到：两次检查之间发生又消失的变化，轮询永远看不到；调度排队时定时会晚点。需要「连续观测」的场景这三档里只有常驻服务勉强接近，且它也受机器替换的影响。
  • 后台任务会失控：忘了关的监听、没有完成条件的周期任务、恢复时被重复拉起的工作，都是真实风险。对应的闸就是本章反复出现的三样：有主契约、完成条件与截止时间、恢复先对账。少一样，风险就回来一分。
  • 交付是最隐蔽的失败：配置对了、执行完了、进度也有了，结果没送到用户手里——前四步的成功会掩盖第五步的失败。所以验证要分开做：配置、执行、进度、交付逐项查，定时任务还要回头确认结果真进了对话；一个安静的监听器不等于崩溃，一个在跑的进程也不等于健康。文档明文
  • 服务不等于有权限：常驻服务跑在自己的身份和环境里，不继承工具的连接器与审批。需要外部权限的后台活，要么走受支持的访问路径，要么降级为「侦测到了，唤醒 Agent 来办」。
📌 证据分级小结：三档分工、轮询本质、有主契约、恢复四步、自改进循环清单，均为官方文档明文；Telegram 自动回复的拆解与「承诺先验收」来自本机运行实测；各机制的调度精度、队列实现、唤醒延迟文档未公开，本章不下结论，属合理推断留白区。一句话收尾：后台系统的可信，不在于它从不漏、不从不迟，而在于它先把会漏会迟说在前面，再用登记、对账和交付验证把剩下的风险逐项摁住。
