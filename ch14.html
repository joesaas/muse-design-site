14页面交互与多端

一句话：一个 Agent，多个入口——界面长在哪个壳上、消息从哪个软件进来，它都是同一个人、用同一份记忆干活。

底层设计原理：为什么是「一个 Agent、多个入口」

如果每端一个助手，记忆就碎了。你在手机上交代的事，电脑上的助手不知道；WhatsApp 里说过的话，回 App 还要再说一遍。个人 Agent 的全部价值建立在「它认识完整的你」之上，所以设计上是反的：先有一个常驻的 Agent 和一份统一的会话记录，各端只是它的脸。换手机、换电脑、换软件，换的是入口，不是它。

产出需要固定收纳处，不能全塞进聊天流。聊天流是按时间排的，天然会淹没一切：上周生成的文档、还没动手的建议、进行中的目标，聊几十句就翻不到了。所以界面给了五个固定页签——Chat 管对话、Feed 管小报、Ideas 管建议、Goals 管长期目标、Library 管成果。每个页签只收一类东西，找的时候不用回忆「当时聊到哪了」，按类别去拿就行。这本质上是把「产出」从对话里剥离出来，单独建档。

每端一个设置、一套人格，更不行。如果语气、规矩、权限在手机上是一个样、在电脑上是另一个样，你就没法信任它——你不知道它此刻按哪套在办事。所以身份文件、权限、记忆都是账号级的一份，各端读同一份。端与端之间允许有差异的，只有「怎么操作更顺手」，不允许有「它是谁、它能干什么」的差异。

审批必须能离开主界面，因为协作是异步的。Agent 经常在你不在场时干活：你出门了，它在家里跑任务，跑到一半遇到要花钱、要发消息的动作，需要你点头。如果你必须打开 App、找到那个对话才能批，审批就成了瓶颈——活停在那里，你也多一件惦记的事。所以审批被设计成可以直达手机推送、在通知里就能裁决。界面要服务的不是「你正盯着屏幕的时刻」，而是「你随时可能被打断的日常」。

底层实现原理：同构、特化与分流

多端同构，边界划在「平台能力」上。五个页签、聊天、状态屏在 iOS、Android、Web、Mac 上保持一致，这是同构的部分。特化只发生在平台独有能力处：Mac 是把 Web 界面装进桌面窗口，再叠加菜单栏常驻、Option+空格快速聊天（在任何应用上方弹出一张聊天卡）、按住 fn 在任意应用里听写；Web 有 Cmd+K 全局搜索面板，跨对话、产物、文件、目标一起找，还有一整套键盘快捷键；手机有统一的手势体系——长按消息出菜单、滑动回复、摇一摇报 Bug。原则是：产品语义全端一致，交互手法各用各的顺手。

特化里藏着「入口再分流」的例子。Android 上把 Muse 设为默认助手后，设置里多一个开关：默认助手的对话是续进主聊天，还是另开一段侧聊天。也就是说，「从哪个入口进来的」本身可以成为分流依据——语音随口问的事，未必要污染主聊天的上下文。再如 iPhone 的主屏小部件、Android 的桌面快捷方式，都是把「找到它」这一步压到最短，但点进去仍是同一个 Agent、同一段记录。特化层再怎么变花样，都不许动「一份记录、一套身份」这条底线。

侧聊天是分流，不是分身。所有对话都只在你和你的 Agent 之间，没有群聊、拉不进第三个人（Invite 按钮只是分享推荐码）。主聊天和侧聊天按主题分开，各自有独立的历史；侧聊天的记录不会被抄进主聊天。好处是上下文干净：一个项目一个房间，检索和记忆提炼时不会互相串味。代价是跨房间的信息不自动流动——这是有意的，下文会说靠什么补。

外部通道只是传输层。WhatsApp 这类接入，文档里的定位写得很死：它是某个侧聊天的传送带，不是第二个 Muse。每段对话有一个 UUID；一条用户消息进来时，运行时先把这段对话的 UUID 和当前的绑定关系 captured 下来，回复就属于这段对话。模型不能挑回复发到哪，chat.send_message 也没法从别的对话往这个通道里硬塞一条消息。通道不产生第二份记录——记录只有一份，住在 Muse 这边，WhatsApp 只是它的一个出入口。断开重连也改不了投递目标：排队中的工作不会被改投到替换账号上。文档明文

一致性的底座在服务端，不在各端自觉。举个硬例子：聊天搜索用的是服务端维护的全文索引，覆盖主聊天、全部侧聊天、归档对话和通道接入的对话，全词匹配、不分大小写，结果按时间倒序——你在任何一端搜，搜的是同一份索引。删掉一条消息或一段对话，它同一时刻从索引里消失。记录只有一份、索引只有一份，各端只是同一数据的不同窗口；如果靠每端本地各存一份，删不干净、搜不一致是迟早的事。文档明文

状态屏是可审计面。点头像打开的状态屏有四个页：Activity（它最近干过什么，Web 上运行中的条目还能悬停叫停）、Approvals（待你裁决的请求）、Upcoming（排期与运行历史）、Identity（名字与头像，还能直接打开 MEMORY、SOUL、IDENTITY 三个文件看和改）。它存在的意义是：Agent 背着你做过的事，随时可查、可停、可改。敢把执行权交给它，心理地基就是这一屏。

具体实现方式

为什么不用一条时间线装下全部？因为时间线只回答「最近发生了什么」，回答不了「我有哪些正在进行的目标」「上个月那份报告在哪」。个人 Agent 的产出是复利型的：目标要跨月追踪，文档要反复打开，建议要攒着挑。按类别收纳，等于给每类产出一个稳定的地址；聊天流再长，也冲不走这些地址。五 Tab 的职责分工：

页签只收什么设计要点
Chat主聊天与全部侧聊天对话按主题分流；搜索是服务端全文索引，覆盖主聊天、侧聊天、归档与通道接入的对话，删消息即同步退出索引
FeedAgent 按简报定期写的小报帖新用户先看到随版本发布的固定介绍帖，不取材于用户数据
IdeasAgent 主动提出的建议卡卡片可滑动反馈口味；点了就直接开工
Goals进行中与已完成的目标Android 与 Web 可拖拽排序、嵌套子目标
Library产物、文档、媒体、文件Web 端有侧栏分类与 System files 入口；产物是它的内嵌页签

一次审批的完整路径（从产生到在通知里裁决）：

Agent 执行中遇到需许可的动作
  → 生成审批请求，进入 Approvals 待审队列          // 状态屏里随时可查
  → iOS / Android 推送直达，通知栏自带 Allow / Deny  // 不必先打开 App
  → iOS 需解锁并切到前台才生效；Android 后台即可裁决
  → Android 上划掉通知 = Deny                        // 所以一次拒绝可能只是误划，可再问一句
  → Mac 没有推送，只能在 App 运行时提醒
  → 裁决回到运行时，被卡住的那一步继续或取消

同一请求也能出现在 WhatsApp 里，靠结构化控件作答；裁决归安全层（Sentinel）认定，不认自由文本里的一句「可以」——防止聊天内容被冒充成批准。文档明文

一个 WhatsApp 侧聊天从接入到收发（以官方指南为准）：

  • 接入：在 Muse 里发起连接，App 给出官方安全链接（agent.meta.ai/connect/channel?service=whatsapp），二维码与绑定流程由 App 托管，状态用 connection_status 查（结果带 chat_id、provider、status）。
  • 成形：连上后，Muse 里出现一段持久侧聊天，标题就叫「WhatsApp」。你在 WhatsApp 里发的话进这段对话，它的历史不进主聊天。
  • 收发：入站靠既有配对通道的节奏轮询拉取；你能发图片、文档、语音，Muse 能回图片、视频、音频、文档和自包含 HTML。在这段对话里建的定时任务，结果也回这段对话。
  • 断开：在 Muse 的主聊天里下令断开，历史保留，旧链接的投递权被撤销；WhatsApp 侧自己不能把自己断开。
  • 边界：这条连接只管你和 Muse 的私聊，读不了你自己的 WhatsApp、进不了群；Muse 也不接受「App 撰写的消息」灌进这段对话，来路必须是 WhatsApp 本人。
  • 运行时私域：轮询游标、加密材料、链接身份、媒体状态全部留在运行时内部，不暴露给模型，也没有可供用户改的连接偏好项。排障靠查状态，重连走安全流程——把最容易出事的一层收在最里面。

引用与转发到侧聊天时，数据往哪走？关键规矩是：跨对话没有直通管。一段对话不能把消息推进另一段对话，模型也不能改道投递。内容要跨房间，只有两条路：一是你本人动手——系统分享、从别的 App 分享进来（链接、图片、文本、文件先暂存到输入框，由你按下发送，不自动发）；二是回到目标对话里重新说。服务端搜索倒是能跨主聊天与侧聊天统一检索（那是给你找东西用的只读索引），但「找到」不等于「搬过去」。这条硬边界防的是串话：A 房间的私密内容，不会因为模型「好心」出现在 B 房间。

边界与代价

  • 平台不对齐是常态：手势、设置项、审批体验各端都有差异（比如 iOS 审批要切前台、Android 划掉通知算拒绝、Mac 干脆没推送）。同构保的是语义，不是像素。
  • 通道能力参差：今天正式接入的只有 WhatsApp；Discord、短信没有这类连接。通道支持什么媒体、能不能带审批控件，逐个供应商不同。
  • 侧聊天分流的代价：房间多了，跨房间协作要靠你手动搬运或统一搜索找回来。隔离换来了干净，也牺牲了自动贯通。
  • 机密 VM 上通道整段缺席：消息通道在机密环境里不出现——隐私档位高于便利。
  • 「某端到底有没有这个功能」不能靠猜：官方文档把话说死——界面能力的权威来源是运行时声明（界面控件清单、设备能力描述），文档没列的入口不等于不存在，也可能只是还没上线。多端系统里，拿一端的样子去断言另一端，是最常见的误判来源。
  • 审批体验的平台债：iOS 要解锁切前台、Android 划掉算拒绝、Mac 没推送——同一个裁决动作，三端三种脾气。系统能做的是把这些差异写明、把「拒绝可能只是误划」这类情况留出复核余地，而不是假装体验一致。
