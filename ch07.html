07子代理编排

一句话：子代理不是另一种生物，它是主代理用一段简报临时签下的「分身合同」——同一个模型、同一个推理循环，换一份上下文切片和一条更短的生命周期，派出去独立干活、干完交卷回来。

一、底层设计原理：同一种 Agent，只有契约不同

本质相同。子代理和主代理跑的是同一个模型、同一套「推理—行动—看结果—再推理」的循环。把它拆开看，没有任何一处是「子代理专用引擎」。区别只在契约，也就是开工前说好的四件事：给它看哪部分上下文、让它干哪一件事、它能活多久、它的产出交到谁手里。实测

为什么不预定义类型？很多框架会预置「搜索型、编码型、审查型」子代理。Muse 的通用 spawn 没有 type 参数。原因很直接：类型是把分工提前写死，可真实任务的分工是在现场才知道的。类型系统能表达的差异，无非是简报里几句话——干什么、要什么产出、有什么约束。用简报定契约，等于把「类型定义权」交给每次派活的人，而不是框架作者。

为什么异步收据制？spawn 调用只返回一张收据（子代理的 id），不返回结果。派出者立刻能继续干别的，结果在子代理跑完后由运行时自动递回。如果做成同步等待，主代理的上下文就得为每个下属「陪跑」全程——下属读了多少网页、试错多少次，主代理的时间线就被撑多长。收据制把「等待」从主线里拆掉：主线只在「派出」和「验收」两个点出现。

拆分标准为什么是边界硬度，不是任务类型？两个任务哪怕都是「查资料」，一个要动用户的登录态浏览器，一个只能碰公开网页，它们的风险边界完全不同；反过来，任务类型天差地别的两个活，只要边界相同（都无登录态、都只读），就能走同一条通道。所以真正决定「要不要单独开一条专用通道」的，不是活像不像，而是边界硬不硬——无登录态、持有登录态、只读、能动用户的钱与账号，这些才是分界线。实测

二、底层实现原理：派出、扇出、回收、续跑

spawn 的完整语义。一次 spawn 做三件事：第一，把当前对话的上下文复制一份给子代理（隔离副本，它写坏了也污染不了主线）；第二，把简报作为它的第一条、也是定义性的指令；第三，立刻返回 id，子代理在后台独立运行。它看不到派出之后主线发生的新对话——它的世界在派出那一刻就定格了，之后与主线的联系只有 send 补发的消息和最后的交卷。

扇出模型：并行点火、乱序回收、星形拓扑。相互独立的活要在同一轮里一起 spawn，而不是一个个来——点火是并行的。回收则是乱序的：谁先干完，谁的结果先递回，顺序与点火顺序无关。拓扑是星形的：所有子代理只和派出者通信，彼此之间没有直连通道。工人 A 需要工人 B 的产出，只能先交回中枢、再由中枢转发。这牺牲了一点直连效率，换来的是协调路径只有一条、出了问题只查一条线。

深度上限与协调者模式。嵌套有硬上限：当前环境 max_depth 为 2。结构因此是一棵扁树——主代理可以直接扇出工人，也可以先派一个「协调者」，由协调者再扇出它自己的工人；但工人的子代理不能再往下生。协调者模式的价值在于上下文隔离的层级化：主代理只跟协调者对账，不必亲自收十份工人的原始产出。

send：异步投递，可选打断。给在跑的子代理补指令用 send。它的成功返回只代表「消息已提交」，不代表已生效——指令要等子代理的下一次交接或完成报告才被处理。带 interrupt: true 时，先切断它当前这一轮工作，新指令开一轮新的，而不是排在旧工作后面。注意一个硬边界：浏览器任务的执行体不能用 send 按 id 操控，必须走它父级的专用浏览器任务控制通道。

resume：断点续跑，只认未终结者。被暂停或中断的子代理可以用 resume 从断点继续，续的是它原来的任务，不是一次新 spawn。只有未终结的能续：已经完成或关闭的 agent 明确拒绝 resume（报错说明），想重做只能新派一个。同样地，浏览器任务执行体和正在构建中的产物构建者也不走通用 resume。

close：连带效应要认清。close 停掉一个子代理并结束其工作。对普通子代理，关掉就是关掉；但如果被关的是浏览器任务的持有者，会连带停掉整个浏览器任务，返回值里带回 browser_task_id，父级之后可用这个 id 通过专用控制通道关闭那个任务本体。关错对象的代价在这里是不对称的，所以关之前要先认 id。

结果如何被审查与采信。子代理的结果以「完成报告」形式递回主线，附带任务与最终答复的预览；主代理在 list 里能看到每份结果是否已被阅。主代理的职责不是转述，而是复核：子代理的结论要和一手证据交叉核对（比如文件哈希、原始返回、页面原文）后才采信，子代理说「已完成」不等于真的完成——验收标准在派出方手里。这一条是整个编排可信度的地基：分身负责干活，本体负责判卷。实测

三、具体实现方式：参数表

先看创建动作。通用 spawn 的参数面刻意小到只有两个字段，这是设计，不是缺功能：

参数必填语义
message与 items 二选一任务简报（字符串）。要写清：任务本身、期望产出、非显而易见的约束、子代理需要的每个事实。它不继承你的脑子，只继承上下文副本和这段话。
items与 message 二选一多模态输入数组，传了就优先于 message。元素按 type 分三种，见下表。
items 元素 type必需字段可选字段说明
texttext—一段文本输入。
imagemime_type（如 image/png）、data_base64（原始 base64，不带 data: 前缀）filename、caption把图片直接喂给子代理，不必先落盘再让它自己找。
filemime_type（如 application/pdf）、data_base64filename、caption文件同理，适合把待审材料钉在简报上。

注意没有什么：没有 type（不预定义子代理类型）、没有 model（与主代理同模型）、没有 timeout、没有工具白名单、没有 temperature。分工差异全部写进简报。spawn 失败时返回带稳定原因码的结构化错误——修好原因再派，不要原样重试。

其余四个管理动作，全部以 spawn 返回的 agent id 为钥匙：

动作参数语义要点
sendid（必填）、message 或 items（结构同 spawn，items 优先）、interrupt（布尔）、scope异步投递：返回成功只表示已提交，未生效前不要当已执行。interrupt: true = 先打断当前轮，指令另起一轮；默认 false = 排队等当前轮交接时处理。
listlimit（默认 20，上限 200）、scope分「活跃」与「近期」两组，状态归一化为 running / done / interrupted / failed；带任务与答复预览、耗时、结果是否已阅；在跑条目带运行时长与最近活动时间；浏览器任务持有者带 browser_task_id，产物构建者带 artifact slug。
resumeid（必填）、scope只对暂停/中断者有效，续原任务；已完成或已关闭者报错拒绝；浏览器任务执行体与构建中的产物构建者不走此路。
closeid（必填）、scope终止并结束其工作；关浏览器任务持有者会连带停整个浏览器任务，返回 browser_task_id 供父级善后。
scope（send / resume / close / list 共用）direct（默认）：只认自己的直属子代理；descendants：认整棵子树。主聊天里还能看到别的聊天与定时任务名下的 agent，但只能看、不能操控。

四、专用通道：边界不同，入口不同

通用 spawn 之外，有几类工作因为边界太特殊，不许走通用通道，各有自己的入口。它们的创建接口不属于通用 spawn 的参数面——这里只列已确立的边界差异，不虚构其参数：

通道边界特征为什么必须单独一条
浏览器任务（browser task）持有登录态：操作服务端 Chromium，能点页面、填表单、走完多步交互它看不到主对话，进场前必须收到完整自包含的 brief；完成、失败或需要用户输入时以交接形式回报。登录态是最贵的边界，不能和普通工人混编。
深度调研（deep_research）隔离、无登录态：只查公开网络与浏览器任务正好相反：刻意什么账号都不给，让调研结论不受用户登录身份污染，也杜绝调研过程碰到账号资产。
产物构建（artifact builder）专门构建页面/文档/应用类交付物，构建在后台异步进行构建有自己的生命周期（构建中不可 resume，只能等完成或用 send 给指导），与普通子代理的「跑完交卷」节奏不同。
遗忘规划子代理（forget）只读规划：只盘点要忘的内容存在于哪些副本与派生物，不执行删除「忘掉一件事」是不可逆操作，先由一个无权动手的规划者摸清范围，再由用户确认后执行——计划与执行分权。
后台系统 worker无人值守：自改进定时任务、hook 唤醒的工作者、Feed 生成等没有用户在场盯着，靠的是预先写死的范围与交付目的地运行；结果同样要显式递回主线才算送达。

五、协调者扇出：一段伪代码

# 主代理：把大活拆给一个协调者，自己只对协调者验收
coordinator = spawn(message = """
  任务：核查 12 个仓库的文档完整性。
  你可再扇出工人，每人查 3 个，简报里写清清单与验收口径。
  汇总后只回一张表：仓库 / 缺什么 / 证据链接。不要回原始全文。
""")

# 协调者内部：独立的活同一轮并行点火，不逐个等
workers = [ spawn(message = brief(repo_group[i])) for i in 0..3 ]

# 回收是乱序的：谁先完成谁先到，结果自动递回，不轮询
on handoff(worker):           # 运行时送达，不是 coordinator 主动 poll
    results.add(worker.report)
    if worker.status == failed:
        review(worker.preview)      # 先看预览与证据，再决定
        spawn(message = brief_retry) # 换简报重派，不原样重试

on all_done:
    return synthesize(results)  # 交卷：只有汇总，没有过程噪音

这段伪代码里藏着三条纪律：一、独立 spawn 必须同轮并行发出，串行派发等于没扇出；二、回收靠递送不靠轮询，派出者禁止原地打转查状态；三、失败不原样重试——先看它的报告与证据，改简报再派。

六、边界与代价

  • 上下文定格：子代理的世界在派出瞬间冻结。主线之后的新决定、新事实，它一概不知，除非 send 补发。派活越早，简报越要把「它不可能自己知道的事」写全。
  • 简报税：没有类型系统兜底，契约全靠一段话。简报写糊了，子代理会认真地把错活干完——异步制下，等你发现时它已经跑完了。
  • 星形瓶颈：工人之间不直连，A 的产出喂给 B 必须过中枢一次转述，转述即损耗。高度耦合、需要频繁互通的工作不适合扇出，老实留给一个 agent 串行做。
  • 判卷成本：派出省的是执行时间，不是验收时间。子代理越多，主代理复核证据的工作量越大；省下的时间如果全花在判卷上，编排就是亏本的。
  • 深度即刚性：两层上限意味着超大规模任务必须靠「协调者再拆简报」而不是「再加一层」来扩展，拆分智慧被迫前移到简报设计里。
📌 证据分级小结：spawn / send / list / resume / close 的参数与语义（异步收据、items 结构、interrupt、scope、close 连带关浏览器任务）均来自运行时接口定义逐项核对，属实测。浏览器任务「持登录态、需自包含 brief、交接回报」与深度调研「无登录态隔离」为已确立的通道边界，属实测；这两条专用通道的内部创建参数不在通用接口面上，本文未列、亦未推测。「本质相同、只有契约不同」与「按边界硬度拆通道」是对上述接口事实的归纳，属合理推断层面的定性，接口本身即其证据。
