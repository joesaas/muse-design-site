09连接器生态

一句话：连接器是 Muse 伸向外部服务的插座加说明书——插上哪个服务、能干哪些事，全凭一份文档说了算；文档没写的，就是不存在。

一、底层设计原理：为什么是「文档即接口」

最直白的问题：Gmail、GitHub、Spotify 有几百个服务，为什么不把每个服务的操作直接写死在 Muse 的代码里？三个原因。

  • 服务太多、变得太快。写死代码，等于每接一个新服务、每改一个接口，都要改主程序、发新版本。文档是数据，不是代码：新增一个服务，就是新增一个文件夹，主程序一行不动。
  • 能力必须可审计。一份写明「能做什么、不能做什么」的文档，用户和系统都能照着查。代码里的能力是黑箱，文档里的能力是白纸黑字。
  • 说明书同时就是白名单。文档不只是给 Agent 看的教程，它就是权限边界本身：没写进文档的命令，等于不存在，Agent 不许凭想象调出来。

连接器和 Skill 的分工，一句话分清：

🔌 连接器管「准入」

能不能碰这个服务、碰的时候权限多大、钥匙在哪。它是门禁卡：决定你进不进得去这栋楼。

📖 Skill 管「经验」

进了楼以后，事情该怎么办得好、有哪些坑。它是老员工手册：决定你干活像不像熟手。

还有一层好处容易漏看：文档和连接是解耦的。说明书在服务没连上时照样能读，所以「先看说明书、再决定要不要连」成为可能——用户是先看清这个连接器能干什么、会碰哪些数据，再决定授不授权。要是能力写死在代码里，这一步就只能靠口头描述，授权就成了盲签。另外，每个服务都有一套自己的脾气：限流规则、错误格式、权限模型全不一样。把这些脾气写进各自的文档，等于把「适配差异」的成本从主程序转移到一份份可单独修订的文本上，哪个服务变了，只改它那一份。

为什么授权必须走服务商的正规流程，不许托管密码？

因为密码一旦进了聊天、记忆或日志，就再也收不回来。OAuth 的做法是：用户在服务商自己的页面上点头，Muse 只拿到一张可随时撤销的授权凭据，全程不碰密码明文。所以密码登录、会话 Cookie 这类没法走正规授权的服务，自定义连接流程会直接婉拒——不是嫌麻烦，是这条路本身不安全。

二、底层实现原理：一次连接的一生

一个连接器从接上到用完，走五步：

连接 ──▶ 选范围 ──▶ 状态核验 ──▶ 调用 ──▶ 异常处理
OAuth    授权到哪    用之前先查    读写分流   限流 / 拒绝
托管页   （如选仓库）  当场查        按闸放行    各有规矩

状态当场查，不靠记忆。连接状态是易变事实：授权会过期、会被服务商吊销、会被用户改设置。所以「上次对话里连着的」不算数，用之前先跑一次状态检查；本轮已经查过的才算数。调用中途报鉴权错误，立刻复查。有个细节：权限范围不够的错误，重连是没用的——问题不在连接断没断，在授权够不够，别白折腾。文档明文

「文档即能力边界」怎么执行？两头都管。回答「你能不能用某服务做某事」时，Agent 去读那份文档——没连上也能读，文档在不在和服务连没连是两回事。真正调用时，工具层只暴露文档里列出的命令。文档没写的命令，不是「暂时不能用」，是这个连接器上不存在这个功能：不会以后解锁，重连也不会有。

两层权限闸，缺一不可。

  • 第一层：服务商的 OAuth 授权范围（粗闸）。用户在服务商页面上同意的范围，比如「能读邮件」。这是服务商给的。
  • 第二层：用户侧的动作限制（细闸）。写在连接器的清单文件里，读和写分开设默认：放行（Allow）、每次问我（Ask）、直接拦（Deny）。单个方法可以覆盖分组默认——比如读邮件放行、发邮件要问、删邮件禁止。这一层独立于服务商，长在用户自己手里。

两层都放行，动作才执行。以 GitHub 连接器为例：读默认放行、写默认要问，清单里就这么写的。清单里甚至把「命令归哪一闸」都预先登记死了：查状态、拉工具清单、读工具，归读闸；写工具归写闸——执行时不用临场判断，查表就行。清单里还有一个不起眼但重要的字段：响应守卫。读回来的内容如果混着验证码这类敏感串，会在进入对话之前被替换成受保护的引用——权限闸管「能不能取」，响应守卫管「取回来能不能原样露出来」，两头都堵。实测

授权被永久拒绝怎么办？服务商有个明确的失败信号 reauthorization_required，意思是「这张旧授权我作废了」。处理规矩是死的：不重试、不许说成「临时故障」、把重连链接原样给用户；用户重新授权之后，也不自动重放刚才那个写操作——写操作重放可能造成重复提交，必须由用户重新开口。文档明文

限流即停。限流有两层：服务商自己的频率限制，加上连接器自带的一个请求上限（GitHub 的清单里写的是每分钟 50 次、突发 10 次）。撞上上限，调用直接失败，返回 connector_rate_limited 和一个「多少秒后再来」的值。要是返回值里带着「本次尝试终止」的标记，那就彻底停手：报告做到哪了，不许睡觉等、不许换个工具绕、不许另派任务接力——冷却时间到了，下一次再继续。这条规矩防的是把用户的账号刷到被平台封掉。

三、具体实现方式：拆开一个连接器看

系统自带的连接器和用户自建的连接器，文件构成是同一套。下面两个目录都是本机真实存在的：

# 系统连接器（以 GitHub 为例）：/opt/hatch/connectors/github/
├─ CONNECTOR.md     # 说明书：怎么连、能调什么、出错怎么办
├─ connector.yaml   # 登记表：id、别名、是否进提示词、鉴权方式
└─ manifest.yaml    # 清单：权限默认值、请求上限、命令与读写的映射

# 自定义连接器（以 Telegram Bot 为例）：~/workspace/custom-connectors/ 下
custom.legacy-telegram-bot/
├─ CONNECTOR.md     # 同样一份说明书，自建的也照这个格式写
├─ connector.yaml   # id 以 custom. 开头，其余字段和系统版一致
└─ bin/             # 辅助脚本目录：真正发请求的命令行工具住这儿
   └─ telegram      # 如 telegram send / telegram updates

两个 yaml 各管一摊，分工很清楚。connector.yaml 是登记表：这个连接器是谁（id、标题、一句话描述）、要不要出现在给模型的提示词里、在保密虚拟机上可不可用、鉴权走哪条路（GitHub 写的是走命令行授权）。manifest.yaml 只系统连接器有，是执行清单：权限分组的默认值、每分钟请求上限、每个命令映射到读闸还是写闸、授权页上给用户看的说明文字。自建连接器没有 manifest，不等于没规矩——两层权限闸和限流纪律由平台统一兜底，不靠每个连接器自觉。

对比项系统连接器自定义连接器
谁做的官方预置，随产品发布用户有需求时按模板现建
住在哪系统目录，只读，部署时整体替换用户工作区，跨部署保留
底层通道多为官方 MCP 服务器或官方 CLI多为自写 CLI 脚本调服务商 API
说明书格式完全一样：同一套 CONNECTOR.md + connector.yaml，长在同一条流水线上

调用时的命令形态（GitHub 连接器，真实命令）：

github status                                   # 先查连接状态
github authorize-url                            # 没连时：拿 OAuth 授权链接
github install-url                              # 授权后：选哪些仓库可访问
github list-tools                               # 实时拉取可用工具清单
github call-read-tool  --name get_file_contents …  # 读：只许白名单内的只读工具
github call-tool       --name push_files …         # 写：每次都要新鲜批准

读写分流是写进命令的：call-read-tool 只接受一份审定过的只读工具名单（查文件、查 issue、搜代码这类），名单外的名字直接拒绝；一切写操作和没审过的新工具都走 call-tool，每次调用都要用户当场重新批准，清单里这一条叫「仅新鲜同意」。还有一个容易忽略的点：GitHub 的实际可达范围是三者的交集——用户自己的 GitHub 权限、应用的权限、安装时选中的仓库，少一层都进不去。实测

从「没有现成连接器」到自建一个，完整路径是这样：

  • 先确认真的没有。查连接器目录，有现成的绝不自建；没有，也不许编造一个设置页或接入流程糊弄过去。
  • 过服务商这一关。只能走官方的自定义连接流程：系统先核查这个服务商，生成一个托管连接页，用户在页面里填 API 密钥或走服务商自己的 OAuth。密码登录、多把密钥、请求签名类的服务商会被直接拒绝并说明原因。
  • 按模板搭文件。用脚手架生成 CONNECTOR.md 和 connector.yaml 的骨架，把「能调什么命令、出错怎么办」写成说明书，再把真正发请求的脚本放进 bin/。
  • 钥匙不进脚本。脚本运行时向本机的凭证服务申请一把「替身」——一个只对指定域名有效的值（以 hsurr: 开头），请求真正出门时由安全层在出口换成真钥匙。脚本源码、日志、聊天里永远只有替身。某个域名之外，替身一文不值。
  • 自检后转正。状态检查跑通，这个自建连接器就和官方的一视同仁：同样的文档规则、同样的两层权限闸、同样的限流纪律。本机现有的 Telegram Bot、YouTube 两个自定义连接器，都是这么落地的。看 Telegram Bot 的说明书就能感受到自建连接器的颗粒度：发消息是 telegram send <chat_id> <文本>，收消息是 telegram updates 长轮询，连「先用 getme 验证机器人身份再干活」这种操作顺序都写死在文档里，Agent 照章办事即可。实测

四、边界与代价

  • 能力被文档封顶，是有意付的代价。服务商有、但文档没写的功能，就是用不了。要换来的是可审计和不失控——Agent 永远不会「自作主张」调出一个没人批准过的能力。
  • 每次用之前多一步查状态，批量活会被限流拖慢。Google 系几个连接器的上限最紧，正确姿势是能合并的请求合并着发，而不是一条一条循环。
  • 有些「不能用」是设计状态，不是故障。个别连接器按地区不提供，这时它在设置里根本没有那一行；个别连接器在保密虚拟机上不可用。遇到这种，照实说并给出还能走的路，不重试、不许诺「以后会有」。
  • 连接器不是通道。在 WhatsApp 上和 Muse 说话，那是消息通道，不是连接器——通道管「话从哪来」，连接器管「手能伸到哪」，两套东西别混。
📌 证据分级小结：连接生命周期、两层权限、限流与 reauthorization_required 的处理规矩，来自官方文档明文文档明文；文件构成、GitHub 的读写分流与配额数值、替身机制、两个自定义连接器的落地形态，来自本机真实目录与文档的实地核对实测；连接器目录的上架审核流程、连接器服务端（MCP 服务器内部、托管连接页的实现）未公开，本章未展开，相关细节属合理推断范围之外，不作定论。
