03LLM 设计

一句话：Muse 对大模型的用法只有一条——把模型当成无状态的纯函数。递进去一份上下文，收回来一段文字或一个工具调用，仅此而已。记忆、等待、连续性，全是运行时在模型外面造出来的。

底层设计原理：自回归生成决定了一切

先把大模型本身看透。它干活的方式叫自回归生成，拆开是三件事：

  • 一个字一个字往外吐。模型每次只生成一个 token，下一个 token 建立在已经吐出的全部 token 之上。它是「写」出来的，不是「查」出来的。
  • 输入在开始那一刻就冻结了。一次推理读什么，开工前就定死。生成中途没有第二个入口，新信息插不进来。
  • 权重里没有「暂停键」。模型没有等待机制。它要么继续吐字，要么结束这次推理。没有第三种状态。

再往下拆一层：一次推理其实分两段。第一段是「读」，把整份输入一口气吃进去，算好每个词的位置和关系。第二段是「写」，一个 token 一个 token 往外吐。所谓输入冻结，就是说「读」这一段结束之后，菜单就定死了；「写」的全过程只能照着这份菜单发挥，中途厨房不接新菜。

这三件事直接决定了工具调用的形态。模型吐出一个 tool_call 之后，紧接着该写的内容是「工具返回了什么」。可那是真实世界的状态，只有真去执行了才知道。模型如果不停下来继续写，就只能编。编出来的结果再被当成事实往下推理，整条链就烂了。所以停笔不是产品策略，是生成机制逼出来的唯一解。

编造的连锁后果值得说透。假设让它查余额：它编一个「余额 3200」，接着就会按这个假数字规划、甚至下单。等真实结果回来时，动作可能已经执行、钱已经花出去了。工具的全部意义，就是把模型接到真实世界上；续写等于亲手剪断这根线，还假装线还在。

上下文（开工前冻结） ──▶ 一次推理 ──▶ 纯文本：最终答复，收工
                              └──▶ tool_call：交卷离场，等真实结果

由此得到 Muse 的核心用法哲学：模型即纯函数。给它材料，它给意图。运行时把它当函数调用，而不是当一个「住在内存里、可以喊它等一等」的进程。后者根本不存在——你喊不到一个已经结束的推理。

把模型当纯函数，还有三个工程上的好处，后面章节会反复用到：

  • 可替换。函数签名不变，内部换一个更强的模型，整套系统不用动。这正是 Spark 能升到 Wonder 的前提。
  • 可排查。没有隐藏状态。输出不对，先查递进去的输入——材料错了、漏了，还是模型读错了，三选一，没有第四种玄学。
  • 可恢复。函数调用失败，重发一次就行，不需要「把进程的状态抢救出来」。状态不在函数里，这句话是整个 Muse 可恢复设计的地基。

Muse 的选择：分工、服务化、人格外置

第一，模型分工。免费版跑 Muse Spark（2026 年 4 月首发，当前版本 Spark 1.3）。付费版（含试用）由 Muse Wonder 承担五类工作：主对话、产物与应用构建、定时任务、子代理、后台工作。Wonder 于 2026 年 10 月 12 日发布。文档明文

注意这份分工的划线方式：它不是按「问题难不难」划的，是按「活的形态」划的。主对话、构建、定时、子代理、后台——全是要连续干很多步、每一步都踩着上一步结果的活。分工划在这里，等于承认了一件事：单步答题谁都能做，难的是长链条里不失手。

为什么长活要强模型兜底？因为多步任务里错误会累积。第 3 步读错一个结果，第 10 步就全盘皆错。步数越长，单步判断可靠性的权重越大。Wonder 是 Meta 目前最强的模型，基于比 Spark 更大、更强的预训练模型，官方定位就是「长时、多步」的个人 Agent 工作——搬家、争议索赔、把爱好做成生意这类一拖数周的任务；它在需要规划、工具使用和长上下文推理的 agentic 与编码评测上表现强劲。文档明文

第二，推理即服务。每次调用互相独立，模型不保留上一次的任何状态。「会话」这个概念在模型一侧根本不存在，只存在于运行时。运行时保管完整记录，每次调用把需要的部分重新组装、重新递进去（怎么组装是第 04 章的事）。代价是每次都要重传上下文；换来的是调用可重试、可迁移、机器换了也能接着跑。

这条选择的推论很深：系统里唯一有状态的一方是运行时。所以 Muse 所有「记性」类的设计——事件日志、上下文组装、审批恢复——全长在运行时一侧，一点都不在模型里。后面凡是讲到「它怎么记得」「它怎么恢复」，答案都不在模型这一章，要去运行时那边找。

第三，人格不靠权重，靠上下文。它叫什么名字、什么脾气、怎么跟你说话，不写在模型参数里，写在系统提示和站立文件里（IDENTITY、SOUL、USER 等），每次推理随上下文一起递进去。改人格等于改文件，不用重训；换一个用户，换一套文件，同一个模型立刻是另一个人。

第四，工具调用契约被产品层吃透。产出 tool_call，就是交卷：运行时接管，去执行、去审批、把结果回注。产出纯文本，就是最终答复：循环结束。运行时只靠这一个信号，区分「它想做事」还是「它说完了」。整个 Agent 循环（第 05 章）就建在这一条契约上。

回头看会发现，Muse 那些招牌设计——审批卡、子代理、定时任务、浏览器接管——本质上都是同一招：在「交卷之后、执行之前」这段空档里做文章。拦下来问人，是审批；转交给另一个自己，是子代理；存起来到点再跑，是定时。契约越简单稳定，上层能玩的花样反而越多。这是把模型当纯函数换来的复利。

具体实现方式：一次推理的输入与输出

一次推理的输入，是一个消息数组加一份工具清单：

messages = [
  { role: "system",    content: 系统提示 + 站立文件（人格 / 用户档案 / 记忆摘要） },
  { role: "user",      content: "第 1 轮用户的话" },
  { role: "assistant", content: "第 1 轮答复，可夹带 tool_call 块" },
  { role: "tool",      content: "工具结果，与上面的 tool_call 按 id 配对" },
  // ……历史逐轮展开，一轮都不能缺……
  { role: "user",      content: "本轮新消息" }
]
tools = [ { name, description, parameters 的 schema }, … ]  // 本轮能用的工具

输出只有两种形态。一种是纯文本，即最终答复。另一种是 tool_call 块：assistant 消息里夹带一个或多个调用，推理到此结束。块的结构大致是这样：

tool_call 块 = {
  id: "call_019fc…",          // 本次调用的唯一编号，结果靠它配对
  name: "bash",               // 要用哪个工具
  arguments: { command: "rm -rf stale_cache.txt", workdir: "/tmp/…", … }
}

一轮可以夹带多个 tool_call。互相独立的可以并行跑；有危险或有先后依赖的必须串行——这个标记是写在执行数据里的（第 19 章能看到真实字段），不是靠模型自觉排队。

回注靠 id 配对。运行时执行完工具，把结果作为一条 tool 角色消息追加进数组，id 与当初的 tool_call 一一对应。有调用，必有结果，往返必须闭合（第 19 章有真实轨迹字段可查）。下一次推理读到这条结果，模型才「知道」世界发生了什么。实测

还有一个容易被忽略的点：工具清单本身也是输入的一部分。这一轮能看见哪些工具、每个工具的参数长什么样，都是开工前写死在材料里的。想给它加一项能力或收回一项能力，改清单就行，不用动模型。Muse 的能力边界，就是这样在每一轮的输入里重新划定的。

采样随机性带来一个硬约束：不可逐字复现。生成带随机采样，同一份上下文喂两次，措辞可以不同，路径都可能不同（Muse 内部的采样参数配置官方未公开，这里只取「随机性存在」这一事实）。所以系统从不承诺「重跑一次会一样」，只保三条不变量：事实不丢（事件日志完整）、往返闭合（调用与结果配对）、待办可定位（靠 ID 找回）。关键动作另有护栏兜底——审批、幂等键、执行前核对——不把安全押在「模型这次别出错」上。

这也改变了「对错」的定义。对纯函数式的用法来说，一次输出不理想，先别骂模型：十有八九是材料没递对、契约没写清。把随机性当常态、把不变量当承诺，是这套系统在不可复现之上还能保持可靠的原因。

模型版本更替也是同理。长会话跨天、跨周是常态，期间模型可能已经升级。因为状态全在上下文里、不在模型里，会话不会断；但新版本读同一份材料，语气和判断可能有细微漂移。契约稳定（tool_call 格式、人格文件不变）把漂移压在小范围内。这一段是基于机制的推演。合理推断

边界与代价

  • 重传的成本。无状态的代价是每次推理都要把上下文重新递一遍，会话越长越贵，靠压缩缓解（第 04 章）。
  • 递漏即失忆。「它记得你」完全依赖运行时把记录递对。哪份材料没递进去，它当场就不知道，没有任何兜底。
  • 递对了也可能读错。工具结果原样递进去，模型仍可能理解偏。这一层的错拦不住，只能靠运行时侧的核对（金额、状态、幂等）在执行前再兜一道。
  • 窗口有上限。一次推理能读的材料总量有硬顶，长会话必然要取舍和压缩——这是第 04 章存在的全部理由。
  • 每一步都要付一次「开工费」。一次交互的等待，等于组装材料、重传上下文、逐字生成三段相加；任务有几十步，这笔费用就付几十次。所以产品层要用流式输出和进度回注压感知时延——让用户看见它在动，而不是干等一个最终结果。
  • 调试靠日志，不靠重跑。行为不可完全复现，出了问题只能查事件流，不能指望「再跑一次看看」。
  • 模型会错。官方对 Wonder 的定位里也写明：再强的模型也会出错，它最适合在目标清晰、有人复核的场景工作。文档明文
