PART 1 · 全景

02运维设计

一句话：这台机器随时可以被整台换掉，但你的文件、任务和进度一样都不能丢——做法是把「状态」和「进程」彻底分家：状态全存进持久存储，进程死了就按账本重建。

一、底层设计原理：为什么「进程随时可死」是第一性原理

先看一个事实：Muse 跑在一台虚拟机上，而这台虚拟机并不归它管。平台更新频繁，机器可能被整体替换、重启、迁移。对一个要替用户管长期目标、盯消息、跑定时任务的 Agent 来说，「机器会消失」不是小概率事故，而是必然会发生的日常。

从这个事实往下推，只剩一条路：凡是丢不起的东西，都不能只活在进程的内存里。于是整个系统被劈成两半：

  • 易失的计算：正在跑的模型推理、工具进程、监听脚本——它们是「劳力」，随时可以死，死了换一个顶上。
  • 持久的状态：文件、任务登记、审批记录、检查点、事件流——它们是「账本」，只追加、落磁盘、换机器也跟着走。

这个取舍的代价很明确：每次动手前都要先查账、每推进一步都要记账，系统因此变慢、变啰嗦。换来的好处是：恢复不再是「出故障后的抢修」，而是每次启动都要走的标准动作。一台全新机器接手一个老用户，和一台老机器重启后继续干活，走的是同一套流程——「从账本重建现状」。崩溃恢复和日常启动被合并成同一件事，这是这套运维观的核心：不追求进程不死（追求不到），只保证状态不丢、接手者永远能从账本算出「现在应该是什么样」。文档明文

📌 打个比方：进程是厨师，状态是菜谱和订单本。厨师可以换班、可以请假，只要订单本还在，新厨师翻开就知道哪桌点了什么、哪道菜做到哪一步。把希望寄托在「厨师永不换班」上，才是真正的脆弱。

二、底层实现原理：VM 被替换时，丢什么、不丢什么

机器被替换时，丢失的是全部易失层：正在运行的进程、内存里的推理上下文、临时文件、进程私有的挂载视图。不丢的是整个家目录——它是持久卷，替换时整体搬走。本章写作时实地清点过这台机器的家目录，持久层至少包括：

  • 核心人格与记忆文件（IDENTITY / SOUL / USER / MEMORY 等）平铺在家目录根部；
  • ~/hooks/ 分成四格：definitions（监听定义，JSON 文件）、scripts（检测脚本）、state（状态水位，如 Telegram 监听的 last_update_id）、logs（JSONL 运行日志）；
  • ~/workspace/cron.d/ 按周期分格存放（daily / hourly / runonce / weekly…），这是计划的投影副本，只读——真正的任务登记在运行时手里，改文件不等于改任务；实测
  • ~/config/ 里有工作区状态文件和它的锁文件（workspace-state.json + .lock），并发写靠锁串行化。

恢复的顺序，官方恢复规程写得很死，一共四步，顺序不能乱：

  • 先读账，再动手。启动任何东西之前，先读「持久化的期望状态」：哪些工作已完成、哪些在等用户确认、哪些被取消了、重试上限是多少——全部先保住。一个在等确认的监听器，绝不能被当成「崩溃了」而粗暴重启。文档明文
  • 先补前置条件，再验。依赖（挂载、服务管理器、运行目录）先恢复，然后用一次全新的工具调用验证就绪——因为老进程的挂载视图是私有的，后来挂上的东西它看不见，等再久也没用。
  • 逐个组件对账，独立恢复。每个组件启动前先查它是不是已经在跑，防重复拉起；一个组件超时不能拖住其他组件；部分成功要落记录，下次尝试不重复已完成的部分。
  • 从检查点续跑，并验证真有进展。检查点要定期、原子地写（先写临时文件再改名替换，写一半断电也不会留下半个坏文件）；突然终止可能跳过收尾处理，所以对外部动作（发消息、付款之类），重试前必须先拿着「意图记录和回执」去对端核对结果是否已经生效，拿不准就不重试。文档明文

还有两条容易漏的纪律：取消也是状态。用户取消一个任务时，要先把「停止」落盘再停服务，恢复流程永远不能把用户亲手取消的东西「好心」续上。以及：运行时托管恢复的范围是已保存的 cron、hook、子代理、产物和可续跑的 Agent 工作；用户自己的自定义程序不在托管范围，必须自己备好启动恢复路径——光有 systemd 单元文件和 Restart 设置，不构成恢复路径。文档明文

三、具体实现方式：持久化布局与一次完整的恢复

东西存在哪为什么放这
人格、记忆、规矩家目录根部的一组 Markdown 文件每轮推理都要读，放最顺手处，且用户能直接打开看
会话与事件流运行时的持久存储（按 session 分流）恢复上下文靠重放事件流，它是唯一的「现状账本」
定时任务运行时登记为准；~/workspace/cron.d/ 是按周期分的只读投影登记与展示分离：看计划看投影，改计划走运行时接口
Hook 监听~/hooks/ 四格：definitions / scripts / state / logs定义、代码、水位、日志各就其位；水位独立存放，干跑才不会误消费检测结果
目标工作文件~/workspace/goals/<目标>/，检查点与日志在其 hidden_files每个目标一个账房，检查点跟目标走不跟进程走
工作区状态~/config/workspace-state.json + 锁文件单点状态加锁串行写，防并发写坏
常驻服务单元文件、程序、状态全放持久家目录，用访客 systemd 拉起机器只给一个 minimal 启动目标，单元必须挂到它真正能到达的目标上

把上面拼起来，一次「VM 替换后恢复」实际走的是这条序列：

1. 新 VM 启动 → 家目录（持久卷）挂载完成
2. 运行时读期望状态账本：
   已完成 ✓ 保留 / 待确认 ⏸ 保留 / 已取消 ✕ 保留 / 重试上限照旧
3. 恢复前置条件（服务管理器、挂载、运行目录）
   → 用一次全新调用验证就绪，不信旧进程的视图
4. 逐项对账恢复：
   cron 按登记表重新排期
   hook 先查水位文件，从上次消费处继续轮询
   子代理与可续跑工作按事件流重放定位
   待审批保持 pending 原样，不动它
5. 每个组件独立验收：配置 ✓ / 执行 ✓ / 进展 ✓ / 交付 ✓
   部分失败单独报告，不连坐、不重做已完成项
# 全程没有任何一步依赖「旧进程还活着」

用户侧能感知到的运维面有三处：一是状态屏的 Activity（它干过什么全有账）和 Upcoming（排了什么班一目了然）；二是失败要明说——恢复部分成功就分组件报告，不许用一句「系统异常」糊过去，安静的监听器也不等于崩溃，要分开归因；三是交付单独验收——任务跑完不算完，结果真的回到发起的那个对话才算完，文档把这条单列成验证项。文档明文

四、边界与代价

  • 轮询有时间窗。cron 和 hook 本质都是轮询，两次检查之间的变化可能漏掉、定时可能迟到——恢复得再完美，也买不来「连续观测」。重要的事不能押在轮询精度上。文档明文
  • 恢复有先后，不是瞬间全量。组件逐个对账，大任务从检查点续跑要时间；恢复任务本身也有间隔重试，它提供的是「再试一次」，不是「截止时间前必好」的承诺。
  • 恢复不了的东西要认。没落盘的进程内状态、没写检查点就断电的中间结果、自定义程序自己没备的恢复路径——都救不回来。所以纪律是前置的：状态先行落盘，而不是事后指望打捞。
  • 未公开的部分。运行时内部用什么调度器排 cron、账本的确切存储引擎、替换时的编排顺序细节，官方文档没有展开，本章不猜；能确证的只有恢复规程、托管范围和本机可见的落盘形态。
📌 证据分级小结：恢复四步规程、托管恢复范围、检查点原子写、取消先落盘、「跑完≠送达」四段验证——出自官方运维文档，属文档明文；家目录的持久化布局、hooks 四格、cron.d 只读投影、状态文件加锁——写作时在本机实地清点，属实测；运行时内部的调度与存储实现未公开，相关表述属合理推断，不作定论。
